## [Unreleased] / [未发布]

### Choosing the AES key length / 选择 AES 密钥长度

- Made the file encryption algorithm a real choice: `AES-128-GCM`, `AES-192-GCM`, or `AES-256-GCM`, with AES-256 still the default. The upload page had carried a selector offering `AES-128 / AES-192 / AES-256 / 3DES` that changed nothing at all — it was removed rather than honoured, because 3DES has a 64-bit block, is broken by Sweet32, and was withdrawn by NIST in 2023. The three that remain are one construction at three key lengths, so they share a nonce length, a tag length, and every byte of the envelope layout.
- 文件加密算法现在是一个真实的选择：`AES-128-GCM`、`AES-192-GCM` 或 `AES-256-GCM`，默认仍为 AES-256。上传页此前那个 `AES-128 / AES-192 / AES-256 / 3DES` 下拉框完全不影响实际加密，当时选择删除而非实现它，因为 3DES 分组只有 64 位、已被 Sweet32 攻破，并已于 2023 年被 NIST 废止。保留的三者是同一构造的三种密钥长度，因此 nonce 长度、tag 长度以及信封布局的每一个字节都相同。
- The algorithm name was already framed into AAD-3, so this needed no envelope version bump and no format change: ciphertext written under one algorithm cannot be relabelled as another without the tag failing. `decryptFile` now also refuses a DEK whose length disagrees with the algorithm the metadata names, turning what would surface as an opaque tag mismatch — indistinguishable from tampered ciphertext — into a statement of what is actually wrong.
- 算法名此前就已经被 frame 进 AAD-3，因此本次无需提升信封版本、也不改变格式：某一算法下写出的密文无法被重新标注为另一种而不导致 tag 校验失败。`decryptFile` 现在还会拒绝长度与元数据所声明算法不符的 DEK，把原本表现为「tag 校验失败」（与密文被篡改无法区分）的情况，变成一条说明真实问题的报错。
- The browser is probed for what it can actually do before the menu is drawn. AES-192 is specified but absent from some WebCrypto implementations, and an unsupported key length fails at encryption time with a bare `OperationError` — after the user has chosen it and picked their files. AES-256 is required rather than probed: without it there is no default to fall back to.
- 菜单在绘制之前会先探测浏览器实际支持的算法。AES-192 虽有规范，但部分 WebCrypto 实现并未提供，而不受支持的密钥长度会在加密时以一个光秃秃的 `OperationError` 失败——此时用户已经选好算法并选好文件。AES-256 是必需项而非探测项：没有它就没有可回退的默认值。
- Widened `ck_files_encryption_envelope` as revision `0005_selectable_aes_key_length`. Only the algorithm name widened; the nonce and tag length checks are unchanged, because all three algorithms use 12 and 16 bytes. The account key envelopes — the wrapped AMK and the encrypted private-key bundle — stay AES-256-GCM and their constraints are untouched: they record no algorithm a reader could disagree with, so there is nothing to select and nothing to bind. Downgrading refuses while any AES-128 or AES-192 file exists, rather than dropping rows that are perfectly decryptable.
- 已以 revision `0005_selectable_aes_key_length` 放宽 `ck_files_encryption_envelope`。只放宽了算法名；nonce 与 tag 的长度检查未变，因为三种算法都是 12 和 16 字节。账户密钥信封（包装后的 AMK 与加密私钥包）仍为 AES-256-GCM，其约束未作改动：它们不记录任何读取方可能产生分歧的算法名，因此既无从选择，也无需绑定。只要还存在 AES-128 或 AES-192 的文件，降级就会拒绝执行，而不是删掉那些完全可解密的数据行。
- Added AES-128-GCM and AES-192-GCM known-answer vectors to `docs/crypto/test_vectors.json`, generated with python-cryptography rather than by calling the browser code. This is the check that matters most: the offline recovery path is Python, and an algorithm the recovery script cannot decrypt would produce files nobody can ever get back. The suite 1 vectors are unchanged.
- 已向 `docs/crypto/test_vectors.json` 增加 AES-128-GCM 与 AES-192-GCM 的已知答案向量，由 python-cryptography 生成，而非调用浏览器代码产生。这是最关键的一道检查：离线恢复路径是 Python 实现的，一个恢复脚本无法解密的算法会产生永远拿不回来的文件。suite 1 的原有向量未作改动。

### Who may read the audit trail / 谁有权读取审计记录

Reported from a live test: a recipient could read the whole history of a shared file, and the owner's own Access Records reported zero downloads. Both came from the same place — the rule deciding which rows a caller may see.

来自一次真实测试的反馈：接收方能读取共享文件的完整历史，而所有者自己的访问记录却显示零次下载。两者出自同一处——决定调用方能看到哪些记录的那条规则。

- **A recipient could see what other recipients did.** The file-scoped query skipped the visibility filter entirely, on the reasoning that entitlement had already been checked. But entitlement is not ownership: a recipient holds an ACTIVE grant, so any recipient could read the whole trail — learning that other recipients existed and when each of them downloaded, and continuing to read it after the owner revoked someone else. Owning the file is what earns the right to see who touched it.
- **接收方能看到其他接收方的操作。** 按文件查询时完全跳过了可见性过滤，理由是"权限已经校验过了"。但**有权限不等于是所有者**：接收方持有一个有效授权，因此任何接收方都能读取完整轨迹——从而得知还存在哪些其他接收方、各自何时下载过，甚至在所有者撤销了别人之后仍能继续读到。是"拥有这个文件"才换来"看得见谁碰过它"的权利。
- **An owner saw zero downloads of their own files.** The account-wide query matched only rows where the caller was the actor or the target, and a recipient's download is neither. The owner was blind to exactly the thing the page exists to show.
- **所有者看到自己文件的下载数为零。** 账户级查询只匹配调用方作为操作者或被操作者的记录，而接收方的下载两者都不是。于是所有者恰恰看不见这个页面存在的意义所在。
- Both are now one rule, applied identically whether or not a file is named: **you see what you did, what was done to you, and everything done to a file you own.** An administrator is still unrestricted.
- 现在两者合并为一条规则，且无论是否指定文件都同样适用：**你能看到你做过的、别人对你做的、以及对你拥有的文件所做的一切。** 管理员仍不受限制。
- **"Total Views" was not counting views.** There is no viewer in this product — you download and decrypt, or you do not — so the stat counted every non-download event as one: uploads, shares, revocations, even sign-ins. It is replaced by Downloads and Shares, which are things that actually happened, and each file row now shows its download count and how many people appear in its history.
- **"Total Views" 统计的并不是浏览。** 这个产品里没有"查看器"——你要么下载并解密，要么不——因此该统计把所有非下载事件都算作一次浏览：上传、分享、撤销，甚至登录。现已替换为 Downloads 与 Shares 这两个真实发生过的动作，并且每一行文件会显示它的下载次数以及历史中出现过多少人。
- The privacy assertion is written as the rule itself: **every row a recipient can see must be something they did or something done to them.** A first attempt asserted that the sender's name must not appear at all, which is too strong — "waldo shared this with you" and "waldo revoked your access" name the sender as the actor and are the recipient's to read, because they are about the recipient. What must not appear is a third party's activity: another recipient's download, or the owner's own upload.
- 隐私断言直接写成规则本身：**接收方能看到的每一条记录，必须是他做的、或是别人对他做的。** 第一版断言写成"发送方的名字完全不能出现"，这过强了——"waldo 把文件分享给你"和"waldo 撤销了你的权限"都以发送方为操作者，但它们讲的是接收方，本就该让他看到。真正不该出现的是第三方的活动：另一个接收方的下载，或所有者自己的上传。
- The end-to-end suite gained both cases. Run against the deployment before the fix, they failed exactly as reported — the recipient saw the owner's actions, and the owner counted zero recipient downloads.
- 端到端测试套件补上了这两种情况。在修复前对着线上运行，它们的失败方式与反馈完全一致——接收方看到了所有者的操作，所有者数到的接收方下载次数为零。

### A presentable notification email / 像样的通知邮件

- The share notification is now a designed message rather than a stack of bare paragraphs: a branded header, the one sentence that matters set apart in a callout, a real button, and a muted footer. `email_templates.py` holds the shell so the verification-code email can adopt the same one later.
- 分享通知现在是一封经过设计的邮件，而不是一堆光秃秃的段落：品牌化的页头、把最要紧的那句话单独放进强调框、一个真正的按钮、以及低调的页脚。外层结构放在 `email_templates.py`，验证码邮件日后可以套用同一套。
- Built the way email actually has to be built: tables for layout because Outlook renders through Word, styles inline because Gmail strips most of a `<style>` block, and no images at all — a blocked remote image leaves a hole, and a tracking pixel is not something this product should be sending. A preheader gives the inbox a real preview line instead of a fragment of markup.
- 按邮件真正需要的方式构建：布局用表格，因为 Outlook 通过 Word 渲染；样式内联，因为 Gmail 会剥掉大部分 `<style>` 块；完全不用图片——被拦截的远程图片会留下一个空洞，而追踪像素不是这个产品该发的东西。preheader 让收件箱显示一句真正的预览文字，而不是一段markup 碎片。
- The plain-text alternative says the same thing rather than being a formality. Some clients show it, some people prefer it, and it is what a screen reader reaches first.
- 纯文本版本说的是同样的内容，不是走个形式。有些客户端只显示它，有些人偏好它，而且屏幕阅读器最先读到的就是它。
- Usernames are escaped into the markup and collapsed to a single line in the subject. A username is only length-constrained — there is no character restriction — so unescaped it is a way to put arbitrary HTML into a message the platform sends on someone else's behalf, and a newline in it has no business in a header. Both were live defects caught by writing the tests, not by reading the code: the preheader had been interpolating the raw name.
- 用户名在写入 markup 时会转义，在主题行中会被折叠为单行。用户名只有长度限制、没有字符限制——因此不转义就等于给了一条途径，把任意 HTML 放进平台代他人发出的邮件里；而其中的换行符更不该出现在邮件头中。这两处都是真实缺陷，且是写测试时发现的、不是读代码看出来的：preheader 此前一直在插入未转义的原始用户名。

### Telling someone a file was shared with them / 告知接收方有文件分享给了他

- There had been no notification of any kind. A recipient learned about a share only by opening their file list and noticing something new — which, for a file shared once and never mentioned in person, means never.
- 此前没有任何形式的通知。接收方只能通过打开文件列表、注意到多了个东西才知道有人分享给了他——而对于一个分享过一次、又没人当面提起的文件来说，这等于永远不知道。
- The file list badges how many shared files this browser has not shown yet, cleared when the shared list is opened. A file that stops being shared drops out of the marker, so re-sharing it counts as new again, and signing out clears it so the next person at that machine does not inherit it.
- 文件列表会标记有多少个分享文件是这个浏览器尚未展示过的，打开分享列表后即清除。不再被分享的文件会从标记中移除，因此重新分享会再次算作"新的"；登出会清空标记，使同一台机器上的下一个人不会继承它。
- Optional email, off by default (`SHARE_NOTIFICATION_EMAIL`), so a deployment without working mail does not queue messages nobody receives. It is sent **after** the share has committed and swallows its own delivery failures: a share that succeeded must not be reported as failed, or rolled back, because a mail server was unreachable.
- 可选的邮件通知，默认关闭（`SHARE_NOTIFICATION_EMAIL`），以免在邮件不通的部署里堆积无人接收的消息。它在分享**提交之后**才发送，并自行吞掉投递失败：一次已经成功的分享，不应该因为邮件服务器不可达就被报告为失败，更不该被回滚。
- Share notifications are capped per day (`SHARE_NOTIFICATION_DAILY_CAP`, 40) so they cannot crowd out verification codes. Both draw on the same provider allowance, and they are not equally important: a verification code that fails to send blocks registration and password reset outright, while a missed share notification costs the recipient one glance at their file list. If the count cannot be established the email is skipped rather than sent on a guess — the safe direction is the one that protects code delivery. For scale: the audit log records nine verification emails across the project's entire history against a 100/day, 3000/month allowance.
- 分享通知设有每日上限（`SHARE_NOTIFICATION_DAILY_CAP`，40），以免挤占验证码的配额。两者共用同一份服务商额度，但重要性并不对等：验证码发不出去会直接阻断注册与密码重置，而漏掉一封分享通知只是让接收方多看一眼文件列表。若无法确定当日已发数量，则跳过邮件而不是凭猜测发送——安全的方向是保护验证码的送达。给个量级参照：审计日志显示整个项目历史上共发出九封验证码邮件，而额度是每天 100 封、每月 3000 封。
- **The filename is deliberately not in the email.** The platform's threat model accepts that the server holds filenames, but an email leaves that boundary entirely — it sits in a third-party mailbox, gets indexed, and is forwarded. Naming the sender is enough to prompt the recipient to go and look; naming the file would move metadata somewhere the design never accounted for. The message does say the recipient opens it with their own passphrase, which is the single most confusing thing about this product for a first-time recipient.
- **邮件中有意不包含文件名。** 本平台的威胁模型接受服务端持有文件名这一事实，但邮件完全离开了那个边界——它躺在第三方邮箱里、会被索引、会被转发。写明分享者已足以促使接收方去查看；写明文件名则会把元数据带到设计从未考虑过的地方。邮件正文会说明接收方用自己的 passphrase 打开它，这是初次接收分享的人最容易困惑的一点。

### Taking a share back / 收回已经分享出去的权限

- The share dialog now lists who currently holds the file and can revoke each of them. `GET /files/{id}/shared-users` and `POST /files/{id}/revoke` both existed and neither was ever called, so a share was invisible and irreversible from the interface: no way to see who held a file, and no way to take it back short of calling the API by hand.
- 分享对话框现在会列出当前持有该文件的人，并可以逐个撤销。`GET /files/{id}/shared-users` 与 `POST /files/{id}/revoke` 两个接口早已存在且从未被调用过，因此一次分享在界面上既不可见也不可逆：既看不到谁持有这个文件，也无法收回——除非手工调用 API。
- The owner's own grant is not offered for revocation; the server refuses it as the canonical owner, and showing the button would promise something it will not do.
- 所有者自己的授权不提供撤销按钮；服务端会以"规范所有者"为由拒绝，把按钮摆出来等于承诺一件它不会做的事。
- The dialog states what revoking does and does not do: it stops further access and removes the file from that person's list, and it cannot recover a copy they have already downloaded and decrypted. `docs/SECURITY_FLOWS.md` has always said so; the interface now says it at the moment it matters.
- 对话框明确说明撤销做什么、不做什么：它会阻止后续访问并把文件从对方的列表中移除，但无法收回对方已经下载并解密的副本。`docs/SECURITY_FLOWS.md` 一直是这么写的；现在界面会在真正需要知道的那一刻说出来。
- Sharing no longer closes the dialog. The list of holders is the confirmation that it worked, and closing the dialog would hide the thing that just changed.
- 分享成功后不再关闭对话框。持有者列表本身就是"分享成功了"的确认，关掉对话框反而会把刚刚发生变化的那部分藏起来。

### Who opened this file, and when / 谁在什么时候打开了这个文件

- Every file row now offers its access history: who did what to it, and at what time, rather than a count. `GET /audit-logs/file/{id}` authorizes against the live entitlement and then returns the complete trail for that file **including events performed by other people** — the account-wide listing deliberately does not, returning only rows where the caller is the actor or the target. Nothing in the app had ever called it, so "who downloaded the file I shared" was recorded in full and unreadable.
- 现在每一行文件都可以查看它的访问记录：谁、在什么时间、做了什么，而不只是一个次数。`GET /audit-logs/file/{id}` 会先校验当前的有效授权，然后返回该文件的完整轨迹，**包含其他人执行的操作**——账户级的列表接口有意不这样做，它只返回调用者作为操作者或被操作者的记录。此前应用里从未调用过这个接口，因此"我分享出去的文件被谁下载了"被完整记录着，却无法读取。
- The owner therefore sees the recipients' downloads with timestamps; a recipient opening the same view sees the same trail for a file they legitimately hold, which is what the server has always been willing to answer.
- 因此所有者可以看到接收方的下载记录及其时间；接收方打开同一视图时，看到的是他确实持有的那个文件的同一份轨迹——这本来就是服务端一直愿意回答的内容。
- Separators live inside the text rather than between elements. Vue trims whitespace between elements, which silently ran "Downloaded" and "137.36 KB" together into one word.
- 分隔符放在文本内部，而不是元素之间。Vue 会裁剪元素之间的空白，这会悄无声息地把 "Downloaded" 和 "137.36 KB" 连成一个词。

### Files shared with you are no longer disguised as your own / 别人分享给你的文件不再伪装成你自己的

- The file list now separates "My Files" from "Shared with me". `GET /files` returns both in one list and has always marked which is which with an `owner` boolean — the page simply never read it, so a file someone else owned and shared sat in "My Encrypted Files" looking exactly like one you had uploaded, as though you owned and managed it.
- 文件列表现在把「My Files」与「Shared with me」分开。`GET /files` 本来就把两者放在同一个列表返回，并一直用 `owner` 布尔字段标明区别——只是页面从未读取过它，因此别人拥有并分享给你的文件就躺在「My Encrypted Files」里，看起来和你自己上传的一模一样，仿佛由你拥有和管理。
- A shared row names who shared it. `FileSummaryOut` gained `owner_username`, eager-loaded with the file so a page of a hundred rows does not become a hundred extra queries. "Shared with me" is not much use without saying who by.
- 分享来的行会写明分享者。`FileSummaryOut` 新增 `owner_username`，与文件一起预加载，因此一页一百行不会变成一百次额外查询。「Shared with me」不写明是谁分享的就没什么用。
- Share and delete are hidden on a file you do not own. A recipient's grant carries `can_share=false` and `can_manage=false` — both are hardcoded for non-owner grants — so those buttons could only ever produce a 404. Offering them promised something the server was always going to refuse.
- 对于不属于你的文件，分享与删除按钮会隐藏。接收方的授权中 `can_share=false`、`can_manage=false`——这两项对非所有者授权是硬编码的——因此这些按钮只可能得到 404。把它们摆出来，等于承诺一件服务端注定会拒绝的事。

### Staging hardening / 预发布环境加固

- Added nginx rate limits for secureview.tech. The application already throttles authentication — ten failures per account and fifty per IP inside fifteen minutes — but every attempt below that threshold still costs a database transaction and a full Argon2id verification at 64 MiB, which turns a deliberately expensive password hash into an amplifier. Credential routes now allow twelve requests a minute with a burst of eight; the rest of the API allows ten a second. Verified: nine requests pass and the tenth onward answer 429.
- 已为 secureview.tech 增加 nginx 限流。应用层本就对认证做了限流——十五分钟内每账户十次失败、每 IP 五十次——但在触发阈值之前，每一次尝试仍要付出一次数据库事务和一次 64 MiB 的完整 Argon2id 校验，这会把一个刻意设计得昂贵的密码哈希变成放大器。凭证类路由现在限制为每分钟十二次、突发八次；其余 API 为每秒十次。实测：前九个请求通过，第十个起返回 429。
- Added a fail2ban jail for this site. There was none: both nginx jails on this host read `monash-tracker.error.log`, which belongs to a different project. Twenty rejected credentials from one address in ten minutes now earns an hour's ban. The site also gained its own access log, so the filter reads this site's traffic rather than every site on the host.
- 已为本站增加 fail2ban jail。此前完全没有：这台主机上的两个 nginx jail 读的都是 `monash-tracker.error.log`，那属于另一个项目。现在同一地址十分钟内二十次凭证被拒即封禁一小时。本站同时有了独立的 access log，使过滤器只读本站流量，而不是主机上所有站点的流量。
- Added `Content-Security-Policy` and `X-Frame-Options: DENY`. The page holds decrypted file contents and a passphrase box, so it must never be framed. **`script-src` includes `'wasm-unsafe-eval'`, and must**: Argon2id comes from `hash-wasm`, so without it `WebAssembly.instantiate` is refused and registration, unlocking and every passphrase operation fail. A first attempt at the policy omitted it and did exactly that. `'unsafe-inline'` is allowed for styles only, because Vue writes inline styles for transitions.
- 已增加 `Content-Security-Policy` 与 `X-Frame-Options: DENY`。页面上存在解密后的文件内容和 passphrase 输入框，因此绝不能被嵌入 iframe。**`script-src` 包含 `'wasm-unsafe-eval'`，且必须包含**：Argon2id 来自 `hash-wasm`，缺了它 `WebAssembly.instantiate` 会被拒绝，注册、解锁以及所有 passphrase 操作全部失败。第一版策略漏掉了它，后果正是如此。`'unsafe-inline'` 仅对样式开放，因为 Vue 会为过渡动画写入内联样式。
- `APP_DOCS_ENABLED` now controls whether `/docs`, `/redoc` and `/openapi.json` are mounted. It defaults to true, because the schema costs the team nothing locally and is useful while building; it is set to false on the public staging host, where an anonymous visitor could otherwise read a complete, machine-readable list of every route, its parameters, and the exact shape each one accepts. Disabling un-mounts the routes, so they answer 404 rather than 403 — the absence does not confirm there is something to find.
- `APP_DOCS_ENABLED` 现在控制 `/docs`、`/redoc` 与 `/openapi.json` 是否挂载。默认为 true，因为本地开发时这份 schema 不产生任何成本且很有用；在公网可访问的预发布主机上设为 false——否则任何匿名访问者都能读到一份完整、机器可读的路由清单，包含每个接口的参数及其精确结构。禁用时路由会被整个卸载，因此返回 404 而非 403——这个"不存在"本身不会确认背后有东西可找。
- Checked and found already correct, recorded so nobody has to check twice: ufw denies inbound by default with only 80/443 and the SSH port open; SSH is key-only on a non-standard port with root restricted to keys; MySQL and the backend bind to localhost only; the backend runs as the unprivileged `fypapp` user; TLS is 1.2/1.3 with HSTS; unattended-upgrades is enabled. The pending OpenSSL security update was applied and nginx restarted onto it.
- 检查后确认本就正确、记录在此以免重复排查：ufw 默认拒绝入站，仅开放 80/443 与 SSH 端口；SSH 仅密钥登录且位于非标准端口，root 亦限制为密钥；MySQL 与后端仅绑定 localhost；后端以非特权用户 `fypapp` 运行；TLS 为 1.2/1.3 并启用 HSTS；unattended-upgrades 已启用。已应用待处理的 OpenSSL 安全更新并重启 nginx 使其生效。

### The audit page reads the API it actually has / 审计页改用真实的接口契约

- The records page had been reading fields the API has never sent. `AuditLogOut` in the browser declared `log_id`, `file_id`, `actor_username`, `device` and `location`; the server sends `action`, `resource_type`, `resource_id`, `actor_user_id`, `target_user_id`, `result`, `description`, `metadata`, `created_at`. Every one of the invented fields was optional, so type checking was satisfied and the page silently read `undefined` for all of them: every row collapsed into one nameless group, every actor rendered as "Unknown user", and the device and location columns were permanently "Unknown". The audit trail was on screen and told the reader nothing. The type now mirrors the server exactly.
- 访问记录页此前一直在读取接口从未发送过的字段。浏览器侧的 `AuditLogOut` 声明了 `log_id`、`file_id`、`actor_username`、`device`、`location`；而服务端发送的是 `action`、`resource_type`、`resource_id`、`actor_user_id`、`target_user_id`、`result`、`description`、`metadata`、`created_at`。那些凭空捏造的字段全都是可选的，因此类型检查毫无怨言，页面则默默地把它们全部读成 `undefined`：所有记录塌缩进同一个无名分组，所有操作者都显示为"Unknown user"，设备与位置两列则永远是"Unknown"。审计记录就摆在屏幕上，却什么也没告诉读者。现在该类型与服务端逐字段对齐。
- This also means the filename lookup added in the previous entry never fired: it read `file_id` on every row, got `undefined`, and resolved nothing. A row's subject is `resource_type` plus `resource_id`, and that is what the grouping uses now — with `SHARE` rows filed under the file they are about, since a share belongs in that file's history.
- 这同时意味着上一条记录里新增的文件名查询从未真正生效：它在每一行上读取 `file_id`，得到 `undefined`，因而什么也没解析出来。一条记录的主体是 `resource_type` 加 `resource_id`，现在的分组正是依此进行——并且 `SHARE` 记录会归入它所涉及的那个文件，因为一次共享属于该文件的历史。
- Account-level events — signing in, changing a password, closing an account — belong to no file and now appear under their own "Account activity" heading instead of being grouped beneath a file id they never had. They also carry proper labels rather than falling to the title-case fallback: "Signed in", not "Auth login succeeded".
- 账户级事件——登录、修改密码、注销账户——不属于任何文件，现在归入独立的「Account activity」标题下，而不再被塞进一个它们从来没有的文件 id 之下。它们同样获得了正式的标签，而不是退化到首字母大写的兜底格式："Signed in"，而不是"Auth login succeeded"。
- `AuditLogOut` gained `actor_username` and `target_username`. Both `User` rows are already joined and in hand in the router, so this costs no extra query — and without them the page can only say "someone did this", which is the one thing an audit trail must not say. A share now reads "Shared with junyan".
- `AuditLogOut` 新增了 `actor_username` 与 `target_username`。两个 `User` 行本来就已经在路由里 join 好并持有，因此这不产生任何额外查询——而缺了它们，页面只能说"有人做了这件事"，这恰恰是审计记录最不该说的话。一次共享现在会显示成 "Shared with junyan"。
- Each entry now shows what the action was, who did it, when, and whatever that action has worth adding — the size uploaded, the person shared with, the reason a download was refused — with failures marked. The two permanently-"Unknown" columns are gone rather than left as furniture.
- 每条记录现在显示操作是什么、谁做的、什么时候、以及该操作值得补充的信息——上传的大小、分享给了谁、下载被拒绝的原因——失败的记录会被标出。那两列永远是"Unknown"的内容被删掉了，而不是留作摆设。
- The hash-chain line no longer shows a permission refusal as a finding. `POST /audit-logs/verify-chain` is ADMIN only and recomputes every hash in the table, so restricting it is right — but the page called it for everyone and printed the 403 as red text, so an ordinary user opening their own history was met with what looked like a broken audit log. Not being allowed to run the check now hides the line; a genuine `INVALID` result is called out prominently, because it is the single most important thing this page can say.
- 哈希链那一行不再把权限拒绝当成检查结论来显示。`POST /audit-logs/verify-chain` 仅限 ADMIN 且会重算整张表的哈希，因此限制它是正确的——但页面对所有人都调用了它，并把 403 当作红色错误文本打印出来，于是普通用户打开自己的历史记录时，看到的像是一个坏掉的审计日志。现在无权执行检查会直接隐藏该行；而真正的 `INVALID` 结果会被醒目地标示出来，因为那是这个页面能说出的最重要的一句话。

### Filenames in the audit log / 审计日志中的文件名

- The records page now shows what each file is called instead of `File #<uuid>`. `GET /audit-logs` returns `file_id` and no filename, and the agreed resolution was for the browser to look it up rather than widen the audit response.
- 访问记录页现在显示每个文件的真实名称，而不再是 `File #<uuid>`。`GET /audit-logs` 只返回 `file_id` 而不返回文件名，团队商定的方案是由浏览器自行查询，而不是扩大审计接口的响应。
- Resolved with one list call before any per-file lookups. `GET /files` returns up to 100 summaries at once and covers essentially every file a person has audit entries for, so a user with eight files costs one request rather than eight; only ids that call misses — a file shared to them, most often — are fetched individually, deduplicated and at most four at a time.
- 解析时先做一次列表查询，然后才逐个补齐。`GET /files` 单次最多返回 100 条摘要，基本覆盖了一个用户会有审计记录的全部文件，因此拥有八个文件的用户只需一次请求而不是八次；只有这次调用没覆盖到的 id（最常见的是别人分享给他的文件）才会单独查询，且会去重、并发上限为四。
- Names are resolved after the rows are on screen rather than before. The history is readable without them, and a slow lookup should not hold it back. A file that has been deleted, or whose access was revoked, simply keeps a shortened id: audit entries outlive the files they describe, and what happened to a file is worth showing after the file is gone.
- 文件名在记录渲染之后才解析，而不是之前。没有文件名时历史记录依然可读，一次缓慢的查询不应该拖住它。已被删除、或访问权限已被撤销的文件会保留一个缩短的 id：审计记录的存续时间长于它所描述的文件，而"这个文件发生过什么"在文件消失之后依然值得展示。

### Deleting your own account / 自助注销账户

- Added `POST /auth/delete-account` and a "Delete account" control on the workspace. A forgotten encryption passphrase is unrecoverable by design — the offline recovery workflow cannot recover one, and `POST /keys/me/rewrap` cannot set a new one without the account master key, which is precisely what the forgotten passphrase protects. Starting over is therefore the only remaining path, and it should not require a teammate with database access to perform it by hand.
- 已新增 `POST /auth/delete-account` 接口以及工作台上的"删除账户"入口。遗忘的加密 passphrase 在设计上就不可恢复——离线恢复流程无法恢复它，`POST /keys/me/rewrap` 也无法在没有账户主密钥的情况下设置新的，而账户主密钥恰恰是被这个遗忘的 passphrase 保护的。因此重新开始是唯一剩下的路径，而这件事不应该需要某位有数据库权限的队友手工完成。
- The login password is required again on top of a live session, and the word `DELETE` must be typed. This is the one irreversible action in the application, and a session left open on an unattended machine should not be enough to trigger it. Owned files are soft-deleted with their access grants revoked — a share must not outlive the account that granted it — and the ciphertext is unlinked only after the database commit lands, matching `FileService.delete`: a process that dies midway leaves rows marked DELETED with their objects still present, which the reconcile job can clean, rather than live rows whose ciphertext has already gone.
- 除了有效的会话之外，还需要再次输入登录密码，并键入 `DELETE` 一词。这是本应用中唯一不可逆的操作，一个留在无人看管机器上的会话不应足以触发它。名下文件会被软删除并撤销其访问授权——共享不应比授予它的账户存活得更久——密文则在数据库提交落盘之后才解除链接，与 `FileService.delete` 保持一致：中途崩溃的进程留下的是状态为 DELETED 但对象仍在的数据行（对账任务可以清理），而不是密文已消失的存活数据行。
- The username and email are released so the same person can register again with them. `identifier_exists` does not filter by status, so leaving the original values in place would reserve them forever — and being able to start over is the entire point. The user row itself stays: audit entries reference the user by id, and removing it would take the record of what happened with it. The tombstone address deliberately keeps a real domain, since a reserved TLD registers fine and then breaks serialization wherever the address is read back.
- 用户名与邮箱会被释放，以便本人可以用它们重新注册。`identifier_exists` 不按状态过滤，因此保留原值会让它们被永久占用——而"能够重新开始"正是这件事的全部意义。用户数据行本身保留：审计记录通过 id 引用用户，删除该行会连带抹掉事情发生过的记录。墓碑邮箱有意保留一个真实域名，因为保留 TLD 虽然能注册成功，却会在任何读回该地址的地方导致序列化失败。
- The dialog points at the private key file first. Deleting is the last resort for someone locked out by a forgotten passphrase, not the first thing to try — the `.pem` saved at registration opens the files without the passphrase, and is worth ruling out before destroying anything.
- 对话框会优先引导用户使用私钥文件。对于因遗忘 passphrase 而被锁在门外的用户，删除是最后手段而非首选——注册时保存的 `.pem` 无需 passphrase 即可打开文件，在销毁任何东西之前值得先排除这条路。

### Audit log labels and the download counter / 审计日志标签与下载计数

- Downloads were being recorded all along; the records page just could not see them. It compared `log.action` against the literal `'download'`, while the backend writes `FILE_DOWNLOAD_AUTHORIZED` when a download is served. So the Downloads stat read zero no matter how many files had been downloaded, every event fell through to being counted as a view, and the raw enum name was rendered to the user. Reported as "there is no access or download record" — the records existed and were complete.
- 下载一直都有记录，只是访问记录页看不见它们。页面把 `log.action` 与字面量 `'download'` 比较，而后端在下载被授权时写入的是 `FILE_DOWNLOAD_AUTHORIZED`。因此无论下载过多少文件，"Downloads"统计恒为 0，所有事件都落到"view"分支被计为浏览，而且原始的枚举名被直接渲染给用户。此前被报告为"没有访问记录下载记录"——记录一直存在且完整。
- Actions now carry human labels ("Downloaded", "Shared", "Access revoked") from one shared module, and an action the browser has no label for is titled rather than dropped: the vocabulary grows on the server side, and a record nobody can name is still a record of something that happened.
- 各类操作现在由一个共享模块提供可读标签（"Downloaded"、"Shared"、"Access revoked"），浏览器不认识的操作会转成标题格式显示而非丢弃：这套词表在服务端会继续扩充，而一条叫不出名字的记录仍然是"发生过某件事"的记录。
- A blocked download (`FILE_DOWNLOAD_INTEGRITY_FAILED`) is deliberately not counted as a download. It is a record of an access that did not happen.
- 被拦截的下载（`FILE_DOWNLOAD_INTEGRITY_FAILED`）有意不计入下载数。它记录的是一次并未发生的访问。

### Session lifetime / 会话有效期

- The browser now renews an expiring session instead of failing the next click. The access token lasts 30 minutes and the refresh token 7 days, but the refresh token was discarded at login and never presented — so a tab left open for half an hour answered a bare authorization error to the next action, with nothing on screen saying the session had ended or that signing in again was the fix. A 401 now triggers one refresh and a retry of the request that failed, transparently.
- 浏览器现在会自动续期即将过期的会话，而不是让下一次点击直接失败。Access token 有效期 30 分钟、refresh token 7 天，但 refresh token 在登录时就被丢弃、从未使用过——因此一个开着半小时的标签页会对下一步操作回一句光秃秃的鉴权错误，界面上既不说明会话已结束，也不提示重新登录即可解决。现在遇到 401 会先续期一次并重放失败的请求，整个过程对用户不可见。
- Concurrent 401s share one refresh. The server rotates the refresh token on every call, so three requests failing together and each starting its own refresh would present an already-consumed token twice and turn a recoverable expiry into a forced logout. They now await the same promise.
- 并发的 401 共用同一次续期。服务端每次续期都会轮换 refresh token，因此三个请求同时失败、各自发起续期的话，第二和第三次会提交已被消费的 token，把一次本可恢复的过期变成强制登出。现在它们等待同一个 promise。
- When a session genuinely cannot be renewed, the tokens are cleared and the user is sent to the login page with an explanation and the page they were on, rather than left in a signed-in-looking shell where every request fails. Both tokens are cleared together through one module, so a logout cannot leave a usable refresh credential behind after the access token is gone.
- 当会话确实无法续期时，会清除令牌并把用户送到登录页，附带说明和原本停留的页面，而不是把人留在一个"看起来已登录、但每个请求都失败"的界面里。两个令牌通过同一个模块一起清除，因此登出不会在 access token 已消失后仍留下一个可用的 refresh 凭证。
- The account key's own 15-minute idle relock is unchanged: it is a separate mechanism, it only affects decryption, and it announces itself with the passphrase dialog. The confusing failure being fixed here was always the session, not the key.
- 账户密钥自身的 15 分钟空闲重锁保持不变：那是另一套机制，只影响解密，并且会通过 passphrase 对话框明确告知用户。这里修复的那个令人困惑的失败自始至终都出在会话上，而不是密钥上。

### Recovering with the private key file / 使用私钥文件恢复

- The `.pem` file the registration page hands out can now be used. It was exported once, described as the thing to keep safe, and then read by nothing: every unlock path derived the key from the passphrase, so a forgotten passphrase meant every uploaded file was unreadable even while the user held the key that opens them. The unlock dialog now offers "Forgotten your passphrase?", which takes the key file, verifies it against the account's registered public key, and unlocks the session without a passphrase.
- 注册页发放的 `.pem` 文件现在可以用了。它只导出一次、被郑重告知要妥善保管，然后就再也没有任何代码读取它：所有解锁路径都从 passphrase 派生密钥，因此一旦忘记 passphrase，即使用户手里正握着能打开文件的那把钥匙，已上传的文件也全都读不出来。解锁对话框现在提供「忘记 passphrase？」入口，接收该密钥文件，与账户已注册的公钥校验后，无需 passphrase 即可解锁本次会话。
- The key file is verified before it is trusted, by wrapping a random probe to the account's public key and unwrapping it with the candidate private key. `importKey` accepts any well-formed PKCS#8 RSA key, so without this check a key from a different account would import cleanly and then fail several steps later as an unwrap error on a file — which reads as "this file is damaged" rather than "this is the wrong key".
- 密钥文件在被信任之前会先校验：用账户公钥包装一段随机探针，再用待验证的私钥解开。`importKey` 会接受任何格式正确的 PKCS#8 RSA 密钥，因此若没有这道检查，来自其他账户的密钥会顺利导入，然后在若干步之后以"文件解包失败"的形式报错——读起来像是"这个文件损坏了"，而不是"你用错了密钥"。
- The file is read in the page and never uploaded, and the imported key is non-extractable and decrypt-only, matching what the passphrase path already guarantees. A PKCS#1 file (`BEGIN RSA PRIVATE KEY`, which `openssl genrsa` still emits by default) is now named as such instead of failing inside `importKey` with a bare DataError.
- 该文件在页面内读取、绝不上传；导入后的密钥不可导出且仅可用于解密，与 passphrase 路径已有的保证一致。PKCS#1 格式的文件（`BEGIN RSA PRIVATE KEY`，`openssl genrsa` 至今仍默认输出这种格式）现在会被明确指出格式不对，而不是在 `importKey` 内部抛出一个光秃秃的 DataError。
- The registration page now says what the file is and why it matters: that it is the account's RSA private key, that it is the only way back in if the passphrase is forgotten, that a `.pem` has no associated application on most systems and any text editor opens it, and that because it needs no passphrase the file itself is the secret and does not belong in the Downloads folder. The previous wording said only "save it somewhere safe", which left users unable to tell what they had been given.
- 注册页现在说明了这个文件是什么、以及为什么重要：它是账户的 RSA 私钥；它是忘记 passphrase 之后唯一的退路；`.pem` 在多数系统上没有关联程序，用任意文本编辑器都能打开；以及正因为它不需要 passphrase，文件本身就是密钥，不应该留在下载文件夹里。此前的文案只说了"请妥善保存"，用户无从判断自己拿到的到底是什么。
- **Not covered:** resetting a forgotten passphrase. `POST /keys/me/rewrap` accepts a new protection profile but no new private-key bundle, so it assumes the caller still holds the account master key — which is exactly what a forgotten passphrase denies them. Recovering by key file therefore restores access for the session but leaves the stored passphrase unchanged. Closing that needs a backend contract change; see the PR for the shape.
- **未覆盖：** 重设已遗忘的 passphrase。`POST /keys/me/rewrap` 只接受新的保护配置，不接受新的私钥包，因此它假定调用方仍持有账户主密钥（AMK）——而这恰恰是忘记 passphrase 的用户所不具备的。因此用密钥文件恢复只能恢复本次会话的访问权限，存储的 passphrase 保持不变。要补上这一块需要修改后端契约，具体形态见 PR 说明。

### Sharing a file with another account / 与其他账户共享文件

- Sharing never worked. The dialog posted `{ target_username }`, while `ShareFileRequest` requires `target_user_id`, `target_key_id`, and `wrapped_file_key` and forbids unknown fields — so every attempt was a 422 that the UI reported as "Share request sent". The same shape as the download button before PR #28: a control that looked like a feature and did nothing.
- 共享功能从来没有真正工作过。对话框提交的是 `{ target_username }`，而 `ShareFileRequest` 要求 `target_user_id`、`target_key_id`、`wrapped_file_key` 三个字段并禁止未知字段——因此每一次尝试都是 422，界面却报告"Share request sent"。这与 PR #28 之前的下载按钮如出一辙：一个看起来是功能、实际什么也没做的控件。
- `crypto/share.ts` performs the rewrap `docs/SECURITY_FLOWS.md` specifies: the sender unwraps the file's DEK with their own account key, wraps that same DEK to the recipient's public key, and submits only the resulting ciphertext. The server never learns the DEK; it can check the wrapping's shape but not its contents, which is why it also validates length on arrival.
- `crypto/share.ts` 实现了 `docs/SECURITY_FLOWS.md` 规定的重新包装流程：发送方用自己的账户密钥解开文件的 DEK，再用接收方的公钥包装同一个 DEK，只提交由此得到的密文。服务端始终不知道 DEK；它能检查包装的形态却无法检查其内容，这也是它在接收时同样校验长度的原因。
- Added `GET /keys/users/by-username/{username}/active`. The share contract is expressed in `target_user_id`, but a sender knows a colleague's username, not their UUID — so completing a share from the browser was impossible regardless of the payload bug. Matching is exact and the route is authenticated: it resolves a recipient the sender already knows and is deliberately not a directory that can be searched or listed. It sits one path segment deeper than `/users/{user_id}/active`, so a username that happens to parse as a UUID cannot be routed as one.
- 已新增 `GET /keys/users/by-username/{username}/active`。共享契约以 `target_user_id` 表达，而发送方知道的是同伴的用户名而非 UUID——因此即使没有那个载荷 bug，也无法在浏览器里完成一次共享。该接口仅精确匹配且需要鉴权：它用于解析发送方已经知道的接收人，有意不作为可搜索或可列举的用户目录。它比 `/users/{user_id}/active` 深一层路径段，因此恰好能解析为 UUID 的用户名不会被错误路由。
- Sharing now needs the account key unlocked, and says so by raising the passphrase dialog and resuming afterwards, the same way downloading does. The DEK is reachable only through that key, so this is not an extra hurdle — it is the step that was missing.
- 共享现在需要先解锁账户密钥，并且会像下载那样弹出 passphrase 对话框、解锁后继续。DEK 只能通过该密钥获得，因此这并不是额外增加的门槛——它正是此前缺失的那一步。
- The dialog now states what sharing is: the file is re-encrypted to the recipient's own key in the browser, they open it with their own passphrase and never the sender's, and sharing is per account rather than by link — a file can only be re-encrypted to a key that already exists. A misspelled username is now named as such instead of surfacing a raw validation error.
- 对话框现在说明了共享究竟是什么：文件在浏览器中被重新加密给接收方自己的密钥，接收方用自己的 passphrase 打开、绝不需要发送方的 passphrase；共享按账户进行而非通过链接——文件只能被重新加密给一把已经存在的密钥。用户名拼错现在会被明确指出，而不是抛出一段原始的校验错误。

### Password policy and registration form / 密码策略与注册表单

- Lowered the login-password minimum from 15 characters to 8, and paid for the difference with composition: a password must now draw on at least 2 of uppercase letters, lowercase letters, numbers, and symbols. Fifteen characters with no other rule was the worst of both trades — long enough to push people toward reuse or a sticky note, but still satisfied by `aaaaaaaaaaaaaaa`. Characters are bucketed by Unicode general category, so a non-Latin password is judged by the same rule rather than failing for being non-ASCII. Existing accounts are unaffected: the login and change-password endpoints still accept any password an older policy could have produced.
- 已将登录密码下限从 15 位降到 8 位，并用组成要求补足强度：密码现在必须至少包含大写字母、小写字母、数字、特殊符号四类中的两类。此前"15 位且无其他要求"是两头不讨好——长到足以逼用户复用密码或写在便利贴上，却仍然让 `aaaaaaaaaaaaaaa` 通过。字符按 Unicode general category 分类，因此非拉丁字符的密码适用同一条规则，不会仅因为不是 ASCII 就被拒。存量账户不受影响：登录与修改密码端点仍接受旧策略下可能产生的任何密码。
- Account details are now matched as substrings rather than whole values. The old rule only rejected a password that *equalled* the username or email; `alice2024` sailed through for user `alice`, which mattered little at fifteen characters and matters a great deal at eight. Fragments shorter than three characters are ignored, so the `a` of `a@example.com` does not block every honest password. The deny-list also gained the short common passwords that the lower minimum newly puts in reach (`password1`, `qwerty123`, `12345678`, and friends) — entries below the minimum length are unreachable, since the length check runs first.
- 账户信息现在按子串匹配，而不是整体相等。旧规则只拒绝与用户名或邮箱**完全相同**的密码，用户 `alice` 用 `alice2024` 可以直接通过；在 15 位下这影响有限，在 8 位下影响很大。长度小于 3 的片段会被忽略，因此 `a@example.com` 里的 `a` 不会挡住绝大多数正常密码。弱密码名单同时补入了因下限降低而重新变得可达的短常见密码（`password1`、`qwerty123`、`12345678` 等）——短于下限的条目不可达，因为长度检查先执行。
- Registration and password reset no longer disable their submit button. A greyed-out button cannot explain itself: the user is left comparing their password against a placeholder to guess which rule they missed. Both forms now validate on click, show the specific failing rule under each field, and focus the first field that needs work; a rule also appears early once the user leaves that field. Same for "Send code", which now says the email address is wrong instead of silently refusing to be pressed.
- 注册与重置密码页不再禁用提交按钮。变灰的按钮无法解释自己：用户只能对着 placeholder 猜自己漏了哪条要求。两个表单现在改为点击时校验，在对应字段下方显示具体未满足的那条规则，并把焦点移到第一个待修正的字段；用户离开某个字段后，该字段的问题也会提前提示。"发送验证码"按钮同理，现在会说明邮箱格式不对，而不是默默无法点击。
- Every password input gained a reveal toggle so a typo can be checked before submitting, and the password fields carry a line stating the composition requirement rather than only a length placeholder. Revealing is per field and always starts hidden, so an abandoned tab does not leave a plaintext password on screen.
- 所有密码输入框都增加了明文/密文切换按钮，便于提交前检查输入是否有误；密码框下方增加一行文字说明组成要求，而不再只有一个写着长度的 placeholder。明文切换按字段独立，且默认始终为密文，因此离开的页面不会把明文密码留在屏幕上。
- Hid Edge/Chromium's native `::-ms-reveal` (and `::-ms-clear`) on `PasswordField`, so the browser's built-in eye no longer sits next to the Lucide toggle and look like a double control.
- 已在 `PasswordField` 上隐藏 Edge/Chromium 原生的 `::-ms-reveal`（以及 `::-ms-clear`），避免浏览器自带的眼睛和图标库切换按钮并排出现，看起来像两个控件。
- The encryption passphrase deliberately keeps the 15-character minimum. It is not a login password: it never reaches the server, it wraps the account key, and losing or guessing it costs the user every file they have encrypted, with no reset path. It now has its own named constant so the two limits can move independently.
- 加密 passphrase 有意保留 15 位下限。它不是登录密码：它从不发送到服务端，用于包装账户密钥，一旦遗失或被猜中，用户已加密的全部文件都将无法恢复，且没有重置路径。它现在使用独立命名的常量，两个下限可以各自调整。
- The browser now mirrors the policy in one shared module (`frontend/src/utils/password-policy.ts`) instead of a length constant copied into each page, so the form can name the exact failing rule while the user types. The server stays the authority and re-runs every rule; the common-password deny-list is deliberately not mirrored, so it can grow into a real breached-password corpus without shipping that corpus to every browser.
- 前端现在用一个共享模块（`frontend/src/utils/password-policy.ts`）镜像该策略，而不是把长度常量复制到每个页面，这样表单可以在用户输入时指出具体是哪条规则未满足。服务端仍是权威并会重新执行全部规则；弱密码名单有意不做镜像，以便日后扩充为真正的泄露密码库而无需下发到每个浏览器。

- 已新增 `email_verification_codes` 表（Alembic revision `0004_email_verification_codes`）， 并同步生产 `02-schema.sql` DDL、运行时 CRUD 授权及 `03-verify.sql` 核验期望。数据行只保存 以服务端 secret、用途与规范化地址为密钥的 HMAC-SHA-256 摘要，绝不保存邮件中的验证码； CHECK 约束固定了过期时间、尝试次数上界及 `CONSUMED`/`consumed_at` 不变量。
- Widened the shared `auth_login_throttles` scope enum with four verification buckets so code sending and code checking are rate limited per address and per IP without a second rate-limit mechanism.
- 已扩展共享的 `auth_login_throttles` scope 枚举，新增四个验证码 bucket，使验证码的发送与 校验按邮箱和 IP 分别限流，无需引入第二套限流机制。
- Added `POST /auth/verification-codes/send`, which answers identically whether or not the address has an account and consumes its rate-limit allowance either way, so it cannot be used to enumerate registered users.
- 已新增 `POST /auth/verification-codes/send`；无论地址是否已注册都返回相同响应并同样消耗 限流额度，因此无法被用来枚举已注册用户。
- `POST /auth/register` now requires `verification_code` and stores the account with `email_verified` already true. Added `POST /auth/password-reset`, which consumes the code before judging the username/email pair, writes a new Argon2id hash, and revokes every session family. Reset leaves the key-protection profile and encrypted private-key bundle untouched, so an account never loses access to its encrypted files by resetting a forgotten login password.
- `POST /auth/register` 现在要求 `verification_code`，并直接以 `email_verified` 为真写入 账户。已新增 `POST /auth/password-reset`：先消费验证码再判断用户名/邮箱是否匹配，写入新的 Argon2id 哈希并撤销全部 Session family。重置不会改动密钥保护配置与加密私钥包，因此账户 不会因为重置遗忘的登录密码而失去对已加密文件的访问能力。

- 已新增出站邮件投递，支持 `resend`（HTTPS API）、通用 `smtp` 及仅供开发的 `console` 三种 provider，且只使用 Python 标准库，后端不新增任何依赖。生产配置会拒绝从不真正发信的 `console`。

### Browser account-key enrolment / 浏览器账户密钥注册

- Replaced the registration page with the client-custody enrolment flow: the browser generates the RSA-3072 key pair and a random AMK, derives the KEK with Argon2id, wraps the AMK, encrypts the PKCS8-DER private key under an AMK/HKDF-derived key, and self-tests that both envelopes reopen before any account is created. The passphrase and plaintext private key never leave the browser; the private key is shown once for the user to save.
- 已将注册页替换为客户端托管的密钥注册流程：浏览器生成 RSA-3072 密钥对与随机 AMK，用 Argon2id 派生 KEK 并包装 AMK，再用 AMK/HKDF 派生密钥加密 PKCS8-DER 私钥，并在创建账户前 自测两个信封均可重新打开。Passphrase 与明文私钥绝不离开浏览器；私钥只展示一次供用户保存。
- Removed twelve labels from the client key contract. `key_material` carried algorithm names, format and AAD versions, and the derived key length — twelve fields with exactly one legal value each, which a caller could only repeat back or get a `422` for varying. The API supplies them now, taking the request from 29 leaf fields to 17. Nothing about the cryptography changed: `to_domain()` fills the same values, so stored rows, `*Out` responses, and the RSA-PSS current-key authorization payload are byte-for-byte what they were, and no signing-payload version bump was needed. The KDF cost parameters stay on the wire because they are a per-account choice that lets the cost be raised later without locking out existing accounts, `key_size_bits` stays because it has three legal values and is cross-checked against the modulus of the uploaded key, and `ciphertext_sha256` stays because it is the commitment the authorization signature carries. New unit tests pin both halves: the wire form must rebuild the fully labelled domain object, and each removed field must be rejected as an unexpected field so the boilerplate cannot creep back one line at a time.
- 已从客户端密钥契约中移除十二个标签字段。`key_material` 原本携带算法名、格式版本与 AAD 版本、派生密钥长度——这十二个字段各自只有一个合法取值，调用方要么原样重复，要么因改动而得到 `422`。现在由 API 自行提供，请求从 29 个叶子字段降到 17 个。密码学部分没有任何变化：`to_domain()` 填入完全相同的值，因此存储行、`*Out` 响应以及 RSA-PSS 当前密钥授权载荷逐字节不变，也无需升级签名载荷版本。KDF 开销参数保留在请求中，因为它是按账户的选择，正是它使得日后调高开销而不锁死老账户成为可能；`key_size_bits` 保留，因为它有三个合法取值且会与上传公钥的模数交叉核对；`ciphertext_sha256` 保留，因为它是授权签名所承诺的那个摘要。新增单元测试固定了两端：请求形态必须能重建带全部标签的领域对象，且每个被移除的字段都必须作为多余字段被拒绝，使这些样板无法一行一行地长回来。
- The registration form now collects an encryption passphrase separate from the login password, as required by `docs/SECURITY_FLOWS.md`, and states that losing it makes the encrypted files unrecoverable.
- 注册表单现在按 `docs/SECURITY_FLOWS.md` 的要求收集独立于登录密码的加密 passphrase，并明确 说明遗失后已加密文件不可恢复。
- Completed the previously non-functional reset-password page with code sending, a resend cooldown, and a success state that reports how many sessions were signed out.
- 已补全此前无法使用的重置密码页：支持发送验证码、重发冷却，并在成功后提示被登出的会话数量。
- Registration and login failures now surface the API's `message` and field-level validation detail instead of the bare "Request failed with status code 422" that axios produces by default. The 422 seen during testing was the frontend omitting the required `key_material` field, submitting a password below the 15-character minimum, and submitting an address without a top-level domain; it was never a database fault.
- 注册与登录失败现在会展示 API 返回的 `message` 及字段级校验详情，而不是 axios 默认产生的 "Request failed with status code 422"。测试中出现的 422 源于前端漏发必填的 `key_material` 字段、密码短于 15 个字符下限，以及邮箱缺少顶级域，与数据库无关。

### Timestamps outside the file domain / 文件领域之外的时间戳

- Finished the second-resolution fix across the rest of the application. Sessions, refresh tokens, throttle buckets, verification codes, recovery requests, user rows, and public keys all land in plain `DATETIME` columns, which store no fractional part and which MySQL *rounds* into rather than truncating — so the value a service kept in memory was not the value in the row, and a stored timestamp could sit up to half a second in the future. `auth_service`, `verification_service`, `recovery_service`, `admin_service`, and the key path now settle the value themselves.
- 已在应用其余部分完成秒级精度的修复。会话、刷新令牌、限流桶、验证码、恢复请求、用户行与公钥全部写入普通 `DATETIME` 列——该类型不保存小数部分，且 MySQL 对带小数的值不是截断而是**四舍五入**——因此服务在内存中持有的值与数据行中的值并不相同，存储的时间戳还可能比实际时刻晚半秒。`auth_service`、`verification_service`、`recovery_service`、`admin_service` 以及密钥路径现在自行确定该值。
- Two call sites wrote both precisions from one instant and needed splitting rather than switching: registration creates the user and the public key alongside the two `DATETIME(6)` key-custody rows, and adding a client-wrapped key creates `user_keys` alongside an `encrypted_private_key_bundles` row. Each now takes the truncated value for the second-resolution columns and the full-precision value for the custody columns. Same instant either way, and truncation only ever moves a timestamp backwards, so the two cannot disagree about ordering.
- 有两处调用点会用同一个瞬时值同时写入两种精度，需要拆分而非直接替换：注册在创建用户与公钥的同时会创建两行 `DATETIME(6)` 密钥托管记录；添加客户端包装密钥则在创建 `user_keys` 的同时创建一行 `encrypted_private_key_bundles`。现在两者分别取截断值写入秒级列、取全精度值写入托管列。两者描述的是同一瞬时，且截断只会把时间向更早移动，因此二者在先后顺序上不可能出现矛盾。
- `audit_logs`, `audit_chain_heads`, and the two key-custody tables keep full precision, deliberately. `POST /audit-logs/verify-chain` recomputes each entry's hash from the stored row, so a digit dropped on the way in would leave the whole chain unverifiable; the custody columns were declared with fractional seconds on purpose, and reducing a column's fidelity is not a side effect this change is entitled to have. Verified against MySQL: fifteen second-resolution columns hold no fractional part, six `DATETIME(6)` columns keep theirs, and the chain still reports `VALID` over 34 entries.
- `audit_logs`、`audit_chain_heads` 与两张密钥托管表有意保留全精度。`POST /audit-logs/verify-chain` 会从存储行重新计算每条记录的哈希，写入时丢掉任何一位都会让整条链无法验证；托管列的小数秒也是有意声明的，而降低某一列的保真度并非本次改动有资格产生的副作用。已针对 MySQL 验证：十五个秒级列均不含小数部分，六个 `DATETIME(6)` 列各自保留小数，审计链在 34 条记录上仍报告 `VALID`。
### File search / 文件搜索

- `GET /files` gained an optional `search` parameter, a case-insensitive substring of the original filename applied across every page. The file page's box previously filtered only the rows it had already fetched, so with the list paginated it could answer "no results" for a file that existed on another page — a search that is confidently wrong is worse than no search at all. Matching happens in the database, so `total` now counts matches rather than the account, and paging through a filtered result works.
- `GET /files` 新增可选的 `search` 参数：对原始文件名做大小写不敏感的子串匹配，且作用于全部分页。文件页面的搜索框此前只过滤已经取回的那些行，因此在列表分页之后，它可能对一个存在于其他页的文件回答"无结果"——一个自信地给出错误答案的搜索比没有搜索更糟。匹配在数据库中完成，因此 `total` 现在统计的是匹配数而非账户文件总数，对过滤后的结果翻页也能正常工作。
- LIKE metacharacters are escaped, so `%` and `_` are matched literally. Both are ordinary characters in a filename and a user typing one means it literally; unescaped, a search for `_` would match every single character and a search for `%` would return everything the caller can see. The column collates `utf8mb4_unicode_ci`, so matching is already case- and accent-insensitive without lowering either side and losing the index.
- LIKE 元字符会被转义，因此 `%` 与 `_` 按字面量匹配。这两个字符在文件名中都是普通字符，用户输入它们时表达的就是字面含义；若不转义，搜索 `_` 会匹配任意单个字符，搜索 `%` 则会返回调用方可见的全部文件。该列使用 `utf8mb4_unicode_ci` 排序规则，因此匹配本身已经对大小写与变音符号不敏感，无需对两侧做小写化处理而丧失索引。
- This discloses nothing new. `original_filename` is a cleartext column: the server already stores it, returns it in every listing, and the client binds it into the file AAD precisely because the server could otherwise rewrite it. The query says nothing about content — the ciphertext and the file key stay as opaque to it as to every other query.
- 这不会泄露任何新信息。`original_filename` 本就是明文列：服务端已经存储它、在每次列表响应中返回它，而客户端把它绑定进文件 AAD 恰恰是因为服务端本可以改写它。该查询不涉及任何内容信息——密文与文件密钥对它的不透明程度，与对其他任何查询完全一致。
- The browser now sends the term instead of filtering locally, debounced at 250 ms so it does not cost a request per keystroke, and drops any response a newer search has superseded — without that, the reply that arrives last wins regardless of which query it answered. The box is labelled "Search your files" again, and an empty result says which term found nothing.
- 浏览器现在发送搜索词而不再本地过滤，以 250 毫秒防抖以避免每次击键都产生一个请求，并会丢弃已被更新搜索取代的响应——否则最后到达的那个响应就会胜出，无论它回答的是哪一次查询。搜索框重新标注为 "Search your files"，无结果时会说明是哪个词没有匹配到。

### Encrypted file storage / 加密文件存储

- Stopped a momentary storage outage from permanently destroying access to an intact file. A failed integrity check wrote `CORRUPTED` to `files.status`, and every authorized-access query filtered that status out — so the file vanished from the list, from `GET /files/{id}`, from download, and from the integrity check itself. Nothing in the codebase ever read `CORRUPTED` back or moved it to any other value, which made it a one-way door. The trigger was much cheaper than "the ciphertext was tampered with": a `MISSING` result, raised whenever the object could not be opened, counted the same as a digest mismatch. An unmounted volume, a mistyped `ENCRYPTED_FILE_DIR`, or an NFS hiccup during a single download was therefore enough to hide a file forever, and the owner could not even ask why — the only surviving route was `delete`, and only for someone who still remembered the `file_id` the list would no longer show them.
- 已修复"存储短暂不可用会永久毁掉一个完好文件的可访问性"的问题。完整性检查失败会把 `CORRUPTED` 写入 `files.status`，而所有授权访问查询都会把该状态过滤掉——于是文件从列表、`GET /files/{id}`、下载乃至完整性检查本身同时消失。代码里没有任何位置会重新读取 `CORRUPTED`，也没有任何位置能把它改回其他值，因此这是一扇单向门。而触发条件远比"密文被篡改"廉价得多：只要对象打不开就会产生的 `MISSING` 结果，与摘要不匹配被同等对待。因此一次未挂载的存储卷、一个写错的 `ENCRYPTED_FILE_DIR`，或者某次下载期间的一下 NFS 抖动，就足以永久隐藏一个文件，而文件所有者甚至无从追问——唯一幸存的路径是 `delete`，且仅对还记得 `file_id` 的人有效，而列表已经不会再把这个 ID 显示给他。
- The durable status now moves only for findings about the ciphertext itself. `MODIFIED` still marks a file `CORRUPTED`: the object was readable and its bytes no longer match the digest recorded at upload, which is evidence about content. `MISSING` and `ERROR` no longer touch it, because they describe the environment rather than bytes nobody could read — recording an environment condition in a per-file column is what made an outage indistinguishable from destroyed data. Both results are still written to `integrity_checks` and to the audit log, which is where a transient condition belongs and where an operator can watch it repeat.
- 现在只有关于密文本身的判定才会改变持久状态。`MODIFIED` 仍然会把文件标记为 `CORRUPTED`：对象可读，但其字节已与上传时记录的摘要不符，这是关于内容的证据。`MISSING` 与 `ERROR` 不再改动该状态，因为它们描述的是环境，而不是关于"谁也读不到的那些字节"的结论——把环境状况记进按文件的列，正是让一次故障与数据损毁变得无法区分的原因。两种结果仍会写入 `integrity_checks` 与审计日志，那才是瞬时状况该待的地方，也是运维能观察它是否反复出现的地方。
- A passing verification now restores `ACTIVE`, from either the explicit integrity check or the one that runs on the way out of a download. The status describes the ciphertext as it is now rather than the worst thing ever observed about it, and a file already stranded at `CORRUPTED` in an existing database heals itself the next time it verifies cleanly. A file that is `DELETED` is never resurrected this way.
- 校验通过现在会把状态恢复为 `ACTIVE`，无论触发自显式的完整性检查，还是下载出口处顺带执行的那次校验。状态描述的是密文此刻的样子，而不是它历史上被观察到的最坏情形；已有数据库中已经卡在 `CORRUPTED` 的文件，会在下一次校验通过时自行恢复。处于 `DELETED` 的文件不会被这条路径复活。
- Authorized-access queries now admit `CORRUPTED` alongside `ACTIVE`, so a damaged file stays visible to the people holding a grant on it. Download is not thereby loosened: it was never this filter that protected it, but the verification that runs on the object before the stream is handed over, and that verification still refuses. The visible difference is that the refusal is now an honest `409` on a file the owner can see, instead of a `404` indistinguishable from "no such file". Sharing a knowingly damaged file stays blocked — `SharingService` keeps its own `ACTIVE`-only check, deliberately.
- 授权访问查询现在同时接纳 `CORRUPTED` 与 `ACTIVE`，使受损文件对持有授权的人保持可见。下载并未因此放松：保护它的从来不是这个过滤条件，而是交出数据流之前对对象执行的那次校验，该校验依然会拒绝。可见的差别在于，拒绝现在是针对一个所有者看得见的文件返回诚实的 `409`，而不是一个与"没有这个文件"无从区分的 `404`。分享一个已知受损的文件仍被阻止——`SharingService` 有意保留了它自己的仅 `ACTIVE` 检查。
- Stopped `POST /files/upload` from answering with a `created_at` that was never stored. Most columns in this schema are plain `DATETIME`, which holds no fractional part, and MySQL does not truncate a value that carries one — it rounds it, to the nearest second. A file written at `08:06:34.691352` came back from every later read as `08:06:35`, so the upload response and the file list disagreed about the same row, and the stored instant sat up to half a second in the future. The file, sharing, and integrity services now settle the value themselves through a new `to_second_resolution_utc`, which only ever moves a timestamp backwards.
- 已修复 `POST /files/upload` 返回一个从未被存储过的 `created_at` 的问题。本 schema 中大多数列是普通 `DATETIME`，不保存小数部分；而 MySQL 对带小数的值不是截断而是**四舍五入**到秒。于是一个写入时刻为 `08:06:34.691352` 的文件，此后每次读取都返回 `08:06:35`——上传响应与文件列表对同一行给出不同的时间，并且存储的时刻最多比实际写入时刻晚半秒。文件、分享与完整性服务现在通过新增的 `to_second_resolution_utc` 自行确定该值，且该函数只会把时间向前（更早）移动。
- `to_database_utc` is deliberately left alone and still keeps microseconds. `audit_logs`, `audit_chain_heads`, `user_key_protection_profiles`, and `encrypted_private_key_bundles` are `DATETIME(6)` on purpose: their values are covered by the audit hash chain and the key-custody signatures, and `POST /audit-logs/verify-chain` recomputes each entry's hash from the stored row, so a digit dropped on the way in would make the chain unverifiable. The two helpers now say in their names which kind of column they are for, and a test pins both halves. The remaining second-resolution tables outside the file domain — sessions, refresh tokens, throttles, verification codes, recovery requests — have the same rounding and are deliberately left for a separate change rather than moved here alongside authentication timing.
- `to_database_utc` 有意保持不变，仍然保留微秒。`audit_logs`、`audit_chain_heads`、`user_key_protection_profiles` 与 `encrypted_private_key_bundles` 刻意使用 `DATETIME(6)`：它们的值被审计哈希链与密钥托管签名覆盖，而 `POST /audit-logs/verify-chain` 会从存储行重新计算每条记录的哈希，因此写入时丢掉的任何一位都会让整条链无法验证。两个辅助函数现在从名字上就说明各自适用于哪一类列，并有测试固定这两侧行为。文件领域之外其余的秒级精度表——会话、刷新令牌、限流、验证码、恢复请求——存在同样的舍入问题，但有意留待单独的改动处理，而不是与认证时序一并塞进本次变更。
- `delete_object` now removes the per-file directory along with the object inside it. `publish` creates one directory per `file_id`, and deletion only ever unlinked the object, so every file ever uploaded left a permanent empty directory behind and nothing else was in a position to remove one. Pruning is best effort: `rmdir` refuses a non-empty directory, which is exactly the interlock wanted if a concurrent publish has just written a sibling, and a directory that cannot be removed is inert rather than a reason to fail an otherwise successful delete.
- `delete_object` 现在会连同目录内的对象一起删除该文件专属的目录。`publish` 为每个 `file_id` 创建一个目录，而删除操作此前只解除对象文件的链接，因此每上传过一个文件就永久留下一个空目录，且没有任何其他位置有条件清理它们。清理为尽力而为：`rmdir` 会拒绝非空目录——如果恰有并发的 publish 刚写入了同级对象，这正是我们想要的联锁；而一个删不掉的目录只是无害的残留，不构成让一次本已成功的删除转为失败的理由。

### Browser-side file decryption / 浏览器端文件解密

- The unlocked account key now relocks itself after fifteen minutes without use. Previously it stayed open for as long as the tab did, which on a shared or unattended machine means indefinitely. The clock is reset by *use* rather than by mouse movement: a key nobody has decrypted with for fifteen minutes should relock even if the person is still reading something else in the tab. A download attempted afterwards raises the passphrase dialog again, and the page says why rather than appearing to fail.
- 已解锁的账户密钥现在会在十五分钟无使用后自动重新上锁。此前它会一直保持解锁直到标签页关闭——在共享或无人看管的机器上，这等同于永久解锁。计时由**使用**重置，而不是由鼠标移动重置：一个十五分钟内没有被用于解密的密钥就应该重新上锁，即便使用者还在同一个标签页里看别的内容。之后再发起下载会重新弹出 passphrase 对话框，页面会说明原因，而不是表现为一次失败。
- Split the two authentication failures a download can produce, which had been collapsed into one generic message. `FileKeyUnwrapError` means the account key does not open this file's wrapped key — the ciphertext may be perfectly intact and simply wrapped to a key this account does not hold, which is what a revoked share looks like. `FileIntegrityError` means the ciphertext, or the metadata bound into its AAD, failed authentication: the bytes on offer are not the bytes that were encrypted. Because the AAD covers the filename, MIME type and size, the second also fires when the server serves a document under details it did not have at upload, which is precisely why those fields are bound.
- 已拆分下载过程中可能产生的两类认证失败——它们此前被合并为同一条笼统的提示。`FileKeyUnwrapError` 表示账户密钥打不开该文件被包装的密钥：密文可能完好无损，只是被包装给了本账户并不持有的密钥，被撤销的分享正是这个样子。`FileIntegrityError` 表示密文本身、或绑定进其 AAD 的元数据未通过认证：呈上来的字节并不是当初被加密的那些字节。由于 AAD 覆盖了文件名、MIME 类型与大小，当服务端以上传时并不存在的信息提供某份文档时，同样会触发第二类错误——而这正是绑定这些字段的目的所在。
- An integrity failure now marks the file's row rather than printing a message that the next action overwrites. It is a finding about the file, not a transport hiccup, and it should still be visible after the user has clicked something else.
- 完整性失败现在会标记该文件所在的行，而不是只打印一条会被下一次操作覆盖的提示。它是关于这个文件的判定，而不是一次网络抖动，因此在用户点击了其他内容之后仍应保持可见。


- Implemented download and decryption in the browser, the P0 `TODO.md` had been carrying. Until now a file could be uploaded and never retrieved: the download button fetched the ciphertext and discarded it, reporting "Download request sent", so the plaintext was gone the moment the uploading tab closed. The button now unwraps the file key, decrypts, and hands the original bytes to the browser as a save. Verified end to end in a real browser: a 571-byte file uploaded through the encryption page came back with an identical SHA-256, and the object on disk contains no fragment of the plaintext.
- 已实现浏览器端的下载与解密，即 `TODO.md` 长期挂着的那个 P0。在此之前，文件可以上传但永远取不回来：下载按钮取回密文后直接丢弃，只提示 "Download request sent"，因此上传的那个标签页一关，明文就没了。现在该按钮会解包文件密钥、解密，并把原始字节交给浏览器保存。已在真实浏览器中端到端验证：一个通过加密页面上传的 571 字节文件取回后 SHA-256 完全一致，而磁盘上的对象不含明文的任何片段。
- Opening the account key needs the encryption passphrase, so the file page raises a dialog for it and resumes the download afterwards. The passphrase is discarded as soon as it has done its work; what survives is a non-extractable `CryptoKey` that can decrypt but whose bytes cannot be read back out, held only in module scope so a reload discards it. Keys are cached by id rather than singly: a file stays wrapped to whichever account key was active when it was uploaded, so after a rotation an older file needs its older key, and `GET /keys/me/{key_id}` still serves it. A file wrapped to a key this session has not opened now names that key and offers to unlock it, instead of failing three steps later with an authentication error.
- 打开账户密钥需要加密 passphrase，因此文件页会弹出对话框询问，并在解锁后继续原先的下载。passphrase 在完成其工作后立即丢弃；留下的是一个不可导出的 `CryptoKey`——它能解密，但字节无法被读回——且只存在于模块作用域中，刷新页面即丢失。密钥按 id 缓存而非只保留一个：文件始终被包装到上传时处于活动状态的那个账户密钥，因此密钥轮换之后，较早的文件需要较早的密钥，而 `GET /keys/me/{key_id}` 仍会提供它。若某个文件被包装到本次会话尚未打开的密钥，现在会指明是哪个密钥并提供解锁入口，而不是在三步之后以一个认证错误失败。
- Fixed `deriveKek`, which used the module's Argon2id constants instead of the cost recorded in the account's own protection profile. The cost travels on the wire precisely so it can be raised later without locking out accounts enrolled under the old one; deriving with today's constants against yesterday's profile silently produces a different key and surfaces as "wrong passphrase", which is the least debuggable failure available. Unenrolled code paths still default to the current constants.
- 已修复 `deriveKek`——它使用的是模块内的 Argon2id 常量，而不是账户自身保护配置中记录的开销参数。该开销之所以随请求传输，正是为了日后可以调高而不锁死按旧参数注册的账户；用今天的常量去对昨天的配置做派生，会静默产生一个不同的密钥，并表现为"passphrase 错误"——这是最难排查的失败形式。尚未注册的代码路径仍使用当前常量作为默认值。
- Nothing is written to disk until the AES-GCM tag has authenticated, so a file that fails to decrypt is never saved half-formed. Because the AAD binds the filename, MIME type and size, a server that served a document under a different name would produce a decryption failure rather than a correctly-decrypted file with a misleading name — now covered by a test that changes the filename after upload and requires the decryption to fail.
- 在 AES-GCM 的 tag 通过认证之前不会向磁盘写入任何内容，因此解密失败的文件绝不会以残缺形态被保存。由于 AAD 绑定了文件名、MIME 类型与大小，服务端若以另一个名字提供某份文档，结果会是解密失败，而不是一份被正确解密却带有误导性名称的文件——现在已有测试覆盖：上传后修改文件名，并要求解密必须失败。

### Reconciliation / 对账清理

- Added `backend/scripts/reconcile.py`, which removes the rows and storage objects nothing will ever read again. Four tables grew without bound on ordinary traffic — `user_sessions`, `session_refresh_tokens`, `auth_login_throttles`, `email_verification_codes` — and none of them was ever deleted from: a single failed login left a throttle bucket behind permanently, and every sign-in left a session row long after the session stopped being usable. Nothing reads any of them once they lapse, because expiry is decided from the timestamps at request time rather than from a stored flag, so they were pure accumulation.
- 已新增 `backend/scripts/reconcile.py`，用于清除那些再也不会被读取的数据行与存储对象。有四张表会随日常流量无上限增长——`user_sessions`、`session_refresh_tokens`、`auth_login_throttles`、`email_verification_codes`——而且从来没有任何位置删除过它们：一次失败的登录就会永久留下一个限流桶，每一次登录都会留下一行会话记录，并在该会话早已不可用之后继续存在。它们失效之后不会再被任何代码读取，因为过期是在请求时依据时间戳判定的，而非依赖某个存储的标志位——因此它们纯粹是堆积。
- Storage is reconciled too. A process that dies between publishing a ciphertext object and committing its row leaves an object no row names, and a delete whose unlink failed leaves an object whose row already says `DELETED`; neither is reachable through the API and neither was ever cleaned up. Objects younger than a grace period are ignored, because `publish` writes before the transaction commits and an object that appeared moments ago may belong to a request still in flight — removing it would destroy a file that is about to become real.
- 存储侧同样纳入对账。若某个进程在发布密文对象之后、提交对应数据行之前崩溃，就会留下一个没有任何数据行指向的对象；而一次 unlink 失败的删除，会留下一个数据行已标记为 `DELETED` 的对象。两者都无法通过 API 触及，也从未被清理过。早于宽限期的对象会被跳过，因为 `publish` 在事务提交之前就已写入，一个刚刚出现的对象可能属于仍在处理中的请求——删除它就等于毁掉一个即将成立的文件。
- Reporting is the default and `--apply` is required to delete anything. A reconciler is the kind of job whose bugs are discovered by what it removed, so the first run on a deployment should be read rather than trusted. It never touches `audit_logs` or `audit_chain_heads` — append-only by design, covered by a hash chain that verify-chain recomputes from the stored rows, and the runtime grant is `SELECT, INSERT` precisely so this cannot happen by accident — nor the file tables, the identity and key-custody tables, or `recovery_requests`, where an expired request records that someone asked and nobody acted.
- 默认仅报告，必须显式传入 `--apply` 才会真正删除。对账任务的 bug 往往要靠"它删掉了什么"才被发现，因此在某个部署上的首次运行应当被阅读而不是被信任。它绝不触碰 `audit_logs` 与 `audit_chain_heads`——它们在设计上只追加，受哈希链覆盖，而 verify-chain 会从存储行重新计算该链；运行时授权仅为 `SELECT, INSERT`，正是为了让此类误删不可能发生——也不触碰文件相关表、身份与密钥托管表，以及 `recovery_requests`（一条过期请求记录的是"有人提出过申请而无人处理"这一事实）。
- Verified against MySQL with rows and objects planted on both sides of every boundary: the lapsed session, token, throttle bucket, verification code, orphaned object and stale staged upload were all removed, while a live session, an unexpired token, a bucket that is still blocking someone, an unexpired code and an object written moments ago all survived. `audit_logs` was untouched at 30 rows throughout. The still-blocking bucket is the important one — deleting a bucket resets its counter, so collecting one that is still enforcing a lockout would turn a cleanup job into a way around it.
- 已针对 MySQL 验证，在每条边界的两侧都预先植入了数据行与存储对象：失效的会话、令牌、限流桶、验证码、孤儿对象与陈旧暂存上传全部被清除，而仍然有效的会话、未过期的令牌、仍在封禁某人的限流桶、未过期的验证码，以及刚刚写入的对象则全部保留。全过程中 `audit_logs` 始终为 30 行未被触碰。其中"仍在封禁"的那个桶最为关键——删除一个桶会重置它的计数，因此若清理掉一个仍在执行锁定的桶，就等于把清理任务变成了绕过锁定的手段。
- `deployment/server/mcs21-reconcile.{service,timer}` run it daily. They are tracked but deliberately not installed by the deploy tooling: enabling them is a separate decision, taken after a report-only run has been read on the target deployment.
- `deployment/server/mcs21-reconcile.{service,timer}` 会每日执行它。这两个文件已纳入版本管理，但有意不由部署工具自动安装：启用与否是一个独立的决定，应在目标部署上阅读过一次仅报告的运行结果之后再作出。

### Development environment / 开发环境

- Pinned the sixteen frontend dependencies that were declared as `"latest"`. A `latest` range resolves at install time, so the build a teammate got depended on the day they ran `npm install` rather than on anything in the repository, and a dependency could break the project with no commit to point at. That had already happened: `npm install` was resolving TypeScript 7, which no longer exports `typescript/lib/tsc`, and `vue-tsc` loads exactly that path — so `vue-tsc` crashed on startup with `ERR_PACKAGE_PATH_NOT_EXPORTED`. `vite build` does not type check, so the build kept passing and nothing announced that type checking had stopped running at all. TypeScript is held at `~5.9.0` until `vue-tsc` supports the new compiler; everything else is pinned to the version currently installed.
- 已固定前端十六个声明为 `"latest"` 的依赖版本。`latest` 区间在安装时才解析，因此队友拿到的构建取决于他们哪天执行了 `npm install`，而不取决于仓库里的任何内容；某个依赖也可能在没有任何提交可追溯的情况下弄坏整个项目。这件事已经发生了：`npm install` 解析到 TypeScript 7，而它不再导出 `typescript/lib/tsc`，`vue-tsc` 恰恰加载这个路径——于是 `vue-tsc` 一启动就以 `ERR_PACKAGE_PATH_NOT_EXPORTED` 崩溃。`vite build` 不做类型检查，所以构建始终通过，没有任何信号表明类型检查其实已经完全停止运行。TypeScript 暂时锁在 `~5.9.0`，直到 `vue-tsc` 支持新编译器；其余依赖固定到当前已安装的版本。
