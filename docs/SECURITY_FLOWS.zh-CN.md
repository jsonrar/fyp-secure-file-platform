# 安全流程

[English](SECURITY_FLOWS.md) | 简体中文

这些流程定义事务边界和信任边界。Auth 已实现。上传、下载、共享、访问撤销、
审计查询、恢复及管理员路由处理器仍受 `501 feature_not_implemented` 保护；
下文相应章节描述的是要求，并非功能已经可用的声明。

## 共同前置条件

每个已实现且受保护的请求只通过 `Authorization: Bearer <token>` 接收不透明
访问令牌。API 依赖项使用该令牌的 SHA-256 哈希解析出活跃且未过期的服务端
会话和 ACTIVE 用户，然后提供可信的 `ActorContext`。未知、已禁用、已过期、
已撤销和格式错误的访问凭据都会收到相同的公开认证响应。

请求体、授权标头、密码、访问/刷新令牌、私钥、已包装密钥和明文文件名必须
从应用、代理和追踪日志中排除。所有 Auth 响应均不可缓存。客户端 IP 取自
请求的直接对端；部署必须先配置可信代理边界，才能使用转发地址标头。

## 密码策略

密码在策略评估、哈希和比较前会进行 Unicode NFC 规范化。新密码必须包含
15 至 128 个字符，且不得等于规范化后的用户名、电子邮件地址、电子邮件本地
部分，或本地常见密码阻止列表中的条目。接受的密码使用 `pwdlib` 推荐的
Argon2id 配置进行哈希。当推荐参数发生变化时，登录会升级有效的已存储哈希。

本地阻止列表特意只包含少量高风险默认密码。它适合本 FYP 使用，但不是持续
维护的已泄露密码语料库。生产环境应使用定期更新的来源替换或扩展该列表，
同时不得削弱 15 字符、NFC 或 Argon2id 规则。

## 注册

```text
规范化并验证 username/email/password
  -> 消耗数据库支持的注册 IP 限流桶
       桶键 = HMAC-SHA-256(application secret, scope || client IP)
  -> 检查不区分大小写的 username/email 唯一性
  -> 使用 Argon2id 哈希密码
  -> 生成已配置的 RSA 密钥对（默认 3072 位）
  -> 使用 SHA-256 为规范 DER 公钥生成指纹
  -> 开始一个事务
       插入带公共 UUID 的 USER 账户
       插入公钥及指纹；绝不插入私钥
       在锁定链头的同时追加 AUTH_REGISTERED 审计事件
       提交
  -> 通过 TLS 且带 no-store/no-cache 标头，仅返回一次私钥
```

客户端应强制下载私钥文件，并避免使用浏览器存储。如果已提交事务的响应丢失，
服务器无法重新生成该私钥；这需要未来显式的密钥轮换/恢复工作流。注册绝不
接受来自客户端的角色、状态或验证状态。

## 登录与访问认证

```text
规范化 username
  -> 为账户和直接客户端 IP 派生数据库限流桶
       键 = HMAC-SHA-256(application secret, scope || normalized value)
  -> 在排序后的行锁下检查两个持久化失败桶
  -> 若存在生效中的阻止，则返回 429 和 Retry-After
  -> 获取一个非阻塞的工作进程内存槽；否则立即返回 429
  -> 执行真实或虚拟的 Argon2id 验证
  -> 成功时清除账户桶，否则以原子方式记录已完成的失败
  -> 追加通用失败审计事件，且不包含明文限流标识符
  -> 锁定 ACTIVE 用户，并将有效的旧 bcrypt 哈希透明升级为 Argon2id
  -> 强制执行最大活跃会话数，并逐出最旧的会话族
  -> 生成相互独立的高熵访问凭据和刷新凭据
  -> 在 user_sessions 中只存储访问凭据的 SHA-256
  -> 在 session_refresh_tokens 中存储第 0 代刷新凭据的 SHA-256
  -> 在同一事务中更新上次登录时间并追加 AUTH_LOGIN_SUCCEEDED
  -> 仅返回一次两项原始凭据
```

账户桶和 IP 桶使用不同的限制（为共享网络设置的 IP 阈值有意更高）。MySQL
确保各工作进程间已完成失败次数的一致性，而每个工作进程独立限制进行中的
Argon2 内存占用。这些控制不能替代边缘限流、可信代理配置、过期桶清理或
分布式拒绝服务防护。

每个已认证请求都会哈希其原始访问令牌，并加载对应的用户和会话。在创建
`ActorContext` 前，会检查状态、访问到期时间、绝对到期时间和用户状态。
原始令牌绝不会进入上下文或数据库行。

## 刷新轮换与重放

```text
验证刷新凭据的格式
  -> 哈希令牌，并在不信任令牌的前提下解析其内部 user/session 路由
  -> 按固定顺序锁定用户、父会话，然后锁定刷新令牌记录
  -> 如果已被消耗：
       撤销该会话族中的访问凭据及每一个刷新凭据
       追加 AUTH_REFRESH_REPLAY_DETECTED
       提交撤销并返回通用 invalid_refresh_token
  -> 拒绝已撤销、已过期、非活跃、已禁用或已绝对过期的会话族
  -> 在消耗下一次轮换前，强制执行每会话最短间隔
  -> 将当前代刷新凭据标记为已消耗
  -> 生成一对新的、相互独立的访问/刷新凭据
  -> 替换访问哈希并插入下一代刷新凭据
  -> 追加 AUTH_SESSION_REFRESHED 并提交
```

因此，刷新令牌只能使用一次。轮换不仅消耗先前的刷新令牌，也会使先前的访问
令牌失效。刷新有效期不得超过会话的绝对有效期，所以反复轮换无法创建永不过期
的会话。已锁定的每会话最短间隔会限制刷新记录及全局审计链的增长；部署边缘
限制及基于到期时间的清理/归档对于整体容量而言仍然是必需的。

## 登出、会话撤销与密码修改

- 登出会锁定并撤销当前会话族，包括尚未消耗的刷新令牌。
- 全部登出会撤销已认证账户拥有的每一个 ACTIVE 会话族。
- 会话列表只返回有数量上限的公共元数据和 UUID，绝不返回令牌哈希或内部 ID。
  单个会话的撤销同时受操作者用户 ID 和公共会话 UUID 的范围限制。
- 密码修改会先读取并验证当前哈希，再获取用户写锁，然后在锁内重新检查哈希，
  才执行更新。它会应用完整密码策略，写入新的 Argon2id 哈希，并撤销每一个
  活跃会话族，包括调用者的当前会话。当前密码检查失败使用专用的重新认证
  账户/IP 桶，因此不能锁住公开登录桶；只有已完成的检查才会增加计数。
  客户端必须重新登录。

每次状态变更及其审计事件共享一个应用服务事务。

## 需要外部通道的 Auth 功能

忘记密码重置、电子邮件验证、MFA 和外部身份联合尚未实现。安全实现分别需要
可信的恢复传递通道、已验证的电子邮件传递、已登记的第二因素保管，或已配置的
身份提供商。在没有这些信任锚点的情况下添加未认证端点，会产生账户接管路径。
`email_verified` 是保留元数据，目前登录时不强制检查。

## 上传（尚未实现）

```text
认证操作者并执行上传大小/类型策略
  -> 在已配置的存储根目录下分配随机暂存对象
  -> 生成一个 AES-256 文件密钥和 96 位 GCM nonce
  -> 通过有版本的 AES-GCM 加密，以流式/有界方式处理上传
  -> 将稳定元数据作为 AAD 进行认证
  -> 哈希完整的加密信封
  -> 分别为所有者和活跃恢复公钥包装 AES 密钥
  -> 开始数据库事务
       插入文件元数据、所有者授权和密钥包装
       追加审计条目，并以原子方式发布暂存对象
       提交
  -> 失败时补偿存储并回滚
```

AES 密钥、存储根目录/路径、暂存名称和已包装密钥字节绝不能出现在响应中。
崩溃产生的孤立对象需要定时对账任务来处理。

## 下载（尚未实现）

```text
认证操作者
  -> 加载限定于该操作者范围内的活跃文件
  -> 要求活跃的 DOWNLOAD 授权及匹配的活跃用户密钥包装
  -> 解密前验证加密对象哈希
  -> 只在专用的不记录请求体端点接收私钥
  -> 验证密钥类型/大小/指纹，并在内存中解包 AES 密钥
  -> 解密/认证，按需添加水印，以流式传输，并清理临时明文
  -> 追加不含秘密字段的成功/失败审计事件
```

计划中的服务端解密流程会暂时接触用户私钥，因此不属于端到端加密。生产环境
应将私钥操作移至可信客户端或硬件支持的密钥服务。

## 共享与撤销（尚未实现）

共享必须认证操作者、要求 SHARE 策略、加载 ACTIVE 目标公钥、重新包装文件
密钥，并以原子方式创建/重新激活授权、密钥包装和审计事件。撤销必须要求
REVOKE 策略、禁止撤销规范所有者，并以原子方式撤销目标授权及匹配的密钥
包装。撤销无法删除接收者已下载的明文。

## 恢复（尚未实现）

恢复必须强制执行经办人—复核人职责分离、有时限的条件状态转换、隔离的私钥
使用，并在同一事务中写入审计事件。生产恢复密钥应置于离线或硬件支持的流程
中；计划中的 Web 流程是一个具有明确约束的 FYP 演示。

## 审计链

```text
锁定单例 audit_chain_heads 行 FOR UPDATE
canonical_event = immutable audit fields 的确定性 JSON
current_hash = SHA-256(previous_hash || canonical_event)
在用例事务内插入审计行并更新链头
```

迁移 `0002_auth_identity_sessions` 只会为空审计表植入创世链头。它会拒绝
非空的 revision-0001 审计历史，因为该版本使用不兼容的载荷，并且已经丢弃
日期时间的微秒；接纳此类数据需要经过审核的迁移和外部检查点。链头锁可防止
并发 Auth 事务使新链产生分叉。条目使用持久化的 `DATETIME(6)` 值和规范的
`{}` 元数据；限制性用户外键可防止级联操作改变经过哈希的操作者/目标 ID；
被历史记录引用的用户必须软删除。数据库内的普通哈希链无法阻止管理员重写并
重新计算全部历史，因此要求更高的部署必须定期在审计数据库之外发布签名/HMAC
检查点。
