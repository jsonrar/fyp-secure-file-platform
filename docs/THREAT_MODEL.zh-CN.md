## 1. 一段话概述系统

浏览器中的 Vue 单页应用完成全部文件与账户密钥的密码学运算。它用全新的数据加密密钥（DEK）加密
每个文件，把该 DEK 分别包装给所有者的 RSA 公钥和一把离线恢复公钥，然后只上传密文。账户私钥在
浏览器中由加密 passphrase 派生的密钥封装，而该 passphrase 从不离开浏览器。位于 nginx 之后的
FastAPI 后端负责会话认证，把密文存放在本地磁盘、把信封存放在 MySQL 8.4，执行共享与恢复策略，
并把每一项安全敏感变更追加进哈希链审计日志。所有组件运行在同一台 VPS 上。参见
[ARCHITECTURE.zh-CN.md](ARCHITECTURE.zh-CN.md) 与 [SECURITY_FLOWS.zh-CN.md](SECURITY_FLOWS.zh-CN.md)。

## 2. 安全目标

| # | 目标 |
|---|---|
| O1 | 在「客户端代码可信、以 API 为边界」的模型下，后端、数据库与存储从不持有读取文件内容或解开 DEK 所需的明文材料——因此攻破或窃取它们都得不到明文。这一点**不**适用于替换了客户端代码的运维者（N1）。 |
| O2 | 文件内容以及绑定进其 AAD 的元数据，无法在不被察觉的情况下被篡改。 |
| O3 | 只有所有者、当前被授权者以及经批准的恢复流程能取得文件密钥。 |
| O4 | 仅凭一份被盗的服务端会话，既无法读取文件，也无法夺取账户的密钥托管权。 |
| O5 | 安全相关操作被记录在日志中，且对日志的悄然改写是可检测的。 |
| O6 | 遗忘的*登录密码*可以找回；遗忘的*加密 passphrase* 只能由持有该账户私钥文件的人找回。 |

## 3. 明确的非目标

以下内容在设计上即不在范围内。把它们写明本身就是模型的一部分：评审者不应把系统并未声称的
保护归功于它。

| # | 非目标 | 原因 |
|---|---|---|
| N1 | 防御**主动作恶的服务器**，即下发被替换的代码、密钥或密文。 | 浏览器执行的是服务器下发的 JavaScript。愿意下发恶意代码的服务器可以窃取 passphrase。零知识成立于 **API 边界**，而不针对代码提供方。参见 [SECURITY_FLOWS.zh-CN.md 的元数据泄露一节](SECURITY_FLOWS.zh-CN.md)。 |
| N2 | **文件元数据**的机密性：文件名、MIME 类型、大小、时间戳、所有权、共享关系图。 | 以明文列存储，以便服务器列出、搜索并执行策略。文件名、MIME 类型与明文大小被绑定进 AAD-3，篡改会在解密时被发现；时间戳、所有权与共享关系图是由服务器控制的明文，不受任何文件 tag 保护。第 3 步将重新评估。 |
| N3 | 匿名性与抵抗**流量分析**。 | 访问时间、IP 地址与密文大小对服务器和网络可见。 |
| N4 | 保护**已被攻破的终端**：恶意软件、恶意浏览器扩展，或站在已解锁键盘前的人。 | 能读取页面的东西就能读取用户解密出的内容。 |
| N5 | **收回**接收方已经取得的明文或密钥。 | 撤销只阻止今后经服务器的访问，无法抹除已完成的下载或已解开的 DEK。 |
| N6 | **没有**私钥文件时找回遗忘的加密 passphrase。 | 服务器不持有任何能打开 AMK 信封的材料。这是实现 O1 的代价。 |
| N7 | 高可用、异地冗余，以及通过任何标准的认证。 | FYP 范围，单台 VPS。 |

## 4. 资产

| ID | 资产 | 存在位置 | 泄露的影响 | 被篡改或丢失的影响 |
|---|---|---|---|---|
| A1 | 文件明文 | 仅在用户浏览器内存中短暂存在 | 该文件机密性完全丧失 | — |
| A2 | 文件 DEK | 浏览器内存；只以 RSA 包装形式存储（`file_key_wrappings`） | 可打开该文件 | 文件不可恢复 |
| A3 | 加密 passphrase | 用户脑中；解锁期间在浏览器内存中 | 配合数据库可打开账户私钥 | 受 O6 约束 |
| A4 | 账户主密钥（AMK） | 解锁期间在浏览器内存中；只以 KEK 包装后的形式存储 | 可打开私钥包 | 账户被锁在门外 |
| A4a | 密钥加密密钥（KEK） | 每次解锁时由 passphrase 经 Argon2id 派生；只存在于浏览器内存中；**从不持久化** | 可打开已存储的包装 AMK | 无可丢失：可由 passphrase 重新派生 |
| A5 | 账户私钥（RSA-3072） | 注册时导出一次的明文 PEM；数据库中的封装私钥包；解锁期间为不可导出的 `CryptoKey` | 可打开包装给该账户的每个文件 | 仅包装给它的文件丢失 |
| A6 | 恢复私钥 | **设计上：**按 [BACKUP_AND_RECOVERY.zh-CN.md 第 7 节](BACKUP_AND_RECOVERY.zh-CN.md)中*提议*的保管方式离线存放。**预发布环境现状：**以未加密 PEM 形式存放在一名团队成员的工作站上（T-I8） | 可打开**每个**文件的恢复包装 | 包装给它的文件无法恢复 |
| A7 | 登录密码 | 用户脑中；数据库中的 Argon2id 哈希 | 夺取服务端会话 | 可通过邮件重置（O6） |
| A8 | 访问令牌与刷新令牌 | 浏览器 `localStorage`；数据库中的 SHA-256 哈希 | 在过期或被撤销前接管会话 | 重新登录 |
| A9 | 密文对象 | VPS 磁盘上由服务用户拥有、权限 0700 的目录；加密备份 | 没有 A2 则无意义 | 完整性失败；从备份恢复 |
| A10 | 文件元数据与共享关系图 | MySQL 明文列 | 隐私损失（N2） | AAD 绑定字段在解密时可发现；其余字段不可 |
| A11 | 审计日志与链头 | MySQL。带 HMAC 认证的外部检查点已经实现，但其在预发布环境上的运行尚未核实（T-T6） | 暴露活动记录 | 篡改必须可被检测（O5） |
| A12 | 服务器秘密：`SECRET_KEY`、数据库凭据、邮件 API 密钥、审计检查点 HMAC 密钥 | VPS 受保护环境与仅 root 可读的文件 | 伪造验证码、数据库访问、滥发邮件、伪造检查点 | 服务中断 |
| A13 | 备份私钥 | 设计上：与 A6 相同的提议保管方式，离线存放。其当前位置未记录在预发布环境安装记录中 | 可打开每一套备份 | 备份不可读 |
| A14 | 已部署代码 | GitHub `main`，由只读部署密钥拉取到 VPS | 见 N1：控制它的人就控制了 A3 | — |

## 5. 参与者与对手

| ID | 参与者 | 正当能力 | 必须不能做到 |
|---|---|---|---|
| U1 | 匿名互联网用户 | 注册、请求验证码、登录 | 暴力破解登录、接触任何文件、枚举账户（仅部分阻止——T-S2） |
| U2 | 已认证 USER | 上传、下载、共享与撤销自己的文件；为自己的密钥申请恢复 | 读取他人文件或元数据；提升角色 |
| U3 | 共享接收方 | 在授权有效期间解密共享给自己的文件 | 没有 `can_share` 时再次共享；撤销后继续经服务器访问 |
| U4 | RECOVERY_OFFICER | 批准或拒绝恢复申请；执行离线重包装 | 批准自己的申请；在线取得文件 DEK；读取明文 |
| U5 | ADMIN | 登记恢复密钥、验证审计链、管理角色 | 读取文件内容或用户私钥 |
| X1 | 网络攻击者 | 观察并修改浏览器与 nginx 之间的流量 | 读取或篡改 TLS 保护下的任何内容（HSTS，`includeSubDomains`） |
| X2 | 被盗会话令牌的持有者 | 在被撤销前以该用户身份调用 API | 读取文件（需要 A3 或 A5）；替换密钥信封（需要 A5——见 T-E3） |
| X3 | 数据库或磁盘窃取者（转储、备份泄露、磁盘镜像） | 读取每一行数据与每个对象 | 读取文件（O1）；只剩针对 A3 的离线 passphrase 猜测 |
| X4 | 恶意或已被攻破的服务器运维者 | X3 的全部能力，外加修改存储数据以及**下发给浏览器的代码** | 仅在 N1 范围内受到约束 |
| X5 | 供应链攻击者 | 发布某依赖的恶意版本，或推送到 `main` | 见 T-T5 与 T-E5 |
| X6 | 拥有仓库写权限的团队内部人员 | 合并到 `main`，随即自动部署 | 绕过评审（目前可以——T-E5） |
| X7 | 恶意接收方 | U3 的全部能力 | 超出 N5 的任何事 |

## 6. 信任边界

```text
            TB1 (TLS)              TB2 (回环)              TB3 (TLS，强制)
[浏览器] ────────────> [nginx] ──────────────> [FastAPI] ─────────────────> [MySQL 8.4]
   │  TB0：明文、                   │                │ TB4（文件系统，0700）
   │  密钥与 passphrase 留在此处    │                └───────────────> [磁盘上的密文]
   │                                │                │ TB5（HTTPS）
   │                                │                └───────────────> [邮件服务商]
   │                         TB6：GitHub main ── 只读部署密钥 ──> [VPS 发布]
   │                         TB7：备份与审计检查点 ──> [异地存储]
   └── TB8：恢复私钥与备份私钥——设计上离线保管；预发布环境现状见 A6
```

| ID | 边界 | 跨越的内容 | 主要控制 |
|---|---|---|---|
| TB0 | 浏览器内部与其他一切之间 | **留在客户端：**文件明文、加密 passphrase、AMK、KEK、明文私钥与 DEK。**会发送到 API：**密文、包装后的密钥、公钥与签名，以及登录密码、验证码、访问令牌与刷新令牌、用户名与邮箱，还有明文元数据——文件名、MIME 类型、大小 | 所有涉及秘密的*密码学运算*都在客户端；认证秘密确实会在 TLS 保护下跨越边界。[SECURITY_FLOWS.zh-CN.md](SECURITY_FLOWS.zh-CN.md) |
| TB1 | 浏览器 ↔ nginx | API 承载的全部内容 | TLS；一年期 HSTS 且含 `includeSubDomains`；80 端口以 308 跳转 |
| TB2 | nginx ↔ FastAPI | 被代理的请求 | 配置为绑定 `127.0.0.1:8000`，受信代理为 `forwarded-allow-ips=127.0.0.1`；线上绑定情况的核查在 OBSERVABILITY 第 8 节中仍为待定 |
| TB3 | FastAPI ↔ MySQL | 信封、元数据、审计记录 | `require_secure_transport=1`；最小权限运行时账户，无 DDL 权限 |
| TB4 | FastAPI ↔ 对象存储 | 密文 | 服务用户拥有权限 0700 的根目录；上传时记录 SHA-256，下载时校验 |
| TB5 | FastAPI ↔ 邮件服务商 | 发往用户地址的验证码 | HTTPS API；验证码只以 HMAC 摘要存储 |
| TB6 | GitHub ↔ VPS | 发布代码 | 只读部署密钥；带数据库核验与隔离机制的发布门禁 |
| TB7 | VPS ↔ 异地存储 | 加密备份、HMAC 检查点 | 备份主机只持有公钥（已在预发布环境安装并运行）。30 天存储桶锁定属于设计的一部分，但预发布环境安装记录中未核实这一项。预发布环境尚未上传任何检查点 |
| TB8 | 联网系统 ↔ 离线保管 | 恢复私钥与备份私钥 | 仅靠流程，且尚未在预发布环境生效（A6）。代码中*确实*强制的是：没有任何端点接受恢复私钥 |

## 7. STRIDE 分析

每条威胁都有稳定的 ID，供后续步骤及发现登记表（第 4 步）引用。

### 7.1 仿冒（Spoofing）

| ID | 威胁 | 控制 | 状态 |
|---|---|---|---|
| T-S1 | 对登录进行密码猜测 | Argon2id 哈希；`auth_login_throttles` 中按账户和按 IP 的限流；nginx `secureview_auth` 每 IP 每分钟 12 次 | 已缓解 |
| T-S2 | 通过注册、发送验证码或重置密码枚举账户 | 发送验证码与重置密码无论账户是否存在都返回相同响应，并同样消耗额度 | 部分——`POST /auth/register` 在用户名**或**邮箱已被占用时返回 `409 account_identifier_unavailable`，且该检查发生在验证码校验*之前*，因此无需有效验证码即可探测是否存在。仅受按 IP 的注册限流约束。第 4 步。 |
| T-S3 | 窃取令牌劫持会话 | 令牌只以 SHA-256 存储；访问令牌 30 分钟、刷新令牌 7 天、绝对时限 7 天；重放刷新令牌会撤销整个会话族（`AUTH_REFRESH_REPLAY_DETECTED`） | 部分——令牌存放位置见 T-I4 |
| T-S4 | 替换**恢复公钥**，使此后每次上传都包装给攻击者 | 浏览器由 PEM 重新计算并显示指纹；从不信任 API 返回的指纹字段 | 部分——没有任何固定机制，需用户带外比对。第 3 步。 |
| T-S5 | 共享时替换**接收方公钥** | 按精确用户名或邮箱解析接收方；浏览器把 DEK 包装给 API 返回的任何 `public_key_pem` | 未决——共享流程既不重新计算、不显示、不固定接收方指纹，也不要求发送方确认。第 3 步。 |
| T-S6 | 伪造邮件验证码 | 10 分钟有效期、尝试次数上限、以 `SECRET_KEY`、用途与地址为密钥的 HMAC 摘要 | 已缓解 |
| T-S7 | 上传时替换**拥有者公钥**，使拥有者自己的那份包装落入攻击者之手 | 浏览器从 `GET /keys/me` 取得拥有者公钥并把 DEK 包装给它 | 未决——与 T-S4、T-S5 一样，没有任何机制固定拥有者自己的公钥。第 3 步会把三者作为同一个公钥身份问题处理。 |

### 7.2 篡改（Tampering）

| ID | 威胁 | 控制 | 状态 |
|---|---|---|---|
| T-T1 | 篡改静态或传输中的密文 | AEAD tag；服务器在下发前还会校验 SHA-256 | 已缓解 |
| T-T2 | 改标文件名、MIME 类型、大小或算法 | 全部绑定进 AAD-3，任何改动都会导致认证失败（[FILE_ENVELOPE.zh-CN.md](crypto/FILE_ENVELOPE.zh-CN.md)） | 已缓解 |
| T-T3 | 用垃圾数据替换用户的密钥信封，把用户锁在门外 | 重包装、添加密钥与 passphrase 重置都要求账户私钥的 RSA-PSS 签名，且各自使用独立的域标签 | 已缓解 |
| T-T4 | 把私钥包、保护配置或文件**回滚**到更早的有效版本 | 乐观 revision 能阻止并发写入，但客户端不固定它上次看到的状态 | 未决——恶意服务器可以下发更早的有效状态。第 3 步。 |
| T-T5 | 恶意依赖版本 | 锁文件；选择 `@noble/ciphers` 是因为它零传递依赖 | 部分——没有来源证明或审计门禁。第 4 步。 |
| T-T6 | 一致性地改写审计日志 | 数据库中的哈希链；`backend/scripts/audit_checkpoint.py` 实现了带 HMAC 认证的外部链头检查点，HMAC 密钥从不交给后端 | 部分——哈希链已在运行。外部检查点存在于仓库中，但预发布环境的首次上传及其主机外验证仍为待定，因此目前还没有外部信任锚在运行。 |
| T-T7 | 在离线恢复期间篡改执行包 | 接受重包装前，服务器重新校验身份、长度与有效授权 | 部分——离线工作站只靠流程（TB8） |

### 7.3 抵赖（Repudiation）

| ID | 威胁 | 控制 | 状态 |
|---|---|---|---|
| T-R1 | 用户否认自己共享、请求下载或重置过 | 每项此类操作都在同一事务中追加审计事件，记录行为者、目标、IP 与 user agent | 就所记录的内容而言已缓解。下载被记录为 `FILE_DOWNLOAD_AUTHORIZED`，写入时机是服务器批准请求并核验密文之后、**开始传输之前**。它证明的是一次获批准的请求，而不是客户端完整收到或解密了数据。 |
| T-R2 | 运维者否认修改过记录 | 外部 HMAC 检查点（T-T6），待其运行后 | 部分——尚未在预发布环境运行；即便运行，也只覆盖链头，不覆盖谁在主机上执行了什么 |
| T-R3 | 恢复专员否认批准或执行过 | 批准与执行是分开审计的事件；申请人不能审批自己的申请 | 部分——同一名专员可以既批准又执行（[SECURITY_FLOWS.zh-CN.md 的离线恢复一节](SECURITY_FLOWS.zh-CN.md)） |

### 7.4 信息泄露（Information disclosure）

| ID | 威胁 | 控制 | 状态 |
|---|---|---|---|
| T-I1 | 数据库或磁盘被盗导致文件内容泄露 | 服务器上没有任何东西能打开 DEK（O1） | 已缓解 |
| T-I2 | 数据库被盗后可进行**离线 passphrase 猜测** | Argon2id，64 MiB、3 轮；最短 10 个字符 | 部分——见[第 9 节](#9-argon2id-成本与-passphrase-最短长度)的实测：KDF 成本足够，但只检查长度会放行几分钟内即可被攻破的 passphrase。 |
| T-I3 | 元数据泄露：文件名、大小、共享关系图 | 访问控制之外没有其他措施 | 接受（N2）；是否加密 manifest 在第 3 步决定 |

| T-I5 | 秘密出现在日志中 | 有书面的排除清单；秘密字段设为 `repr=False`；[OBSERVABILITY 第 7 节](OBSERVABILITY_AND_INCIDENT_RESPONSE.zh-CN.md) | 部分——控制存在于代码中；在预发布环境输出中确认脱敏标记不出现的线上核查，在 OBSERVABILITY 第 8 节中仍为待定 |

| T-I7 | 用户对导出的明文 PEM 处置不当 | 只展示一次并附警告；使用时在本地读取、从不上传 | 接受——保管方式在第 3 步决定 |

| T-I9 | 共享接收方保留已下载的内容 | — | 接受（N5） |

## 8. 滥用场景

逐个端到端推演，并注明各自串联了哪些威胁。

1. **笔记本上的会话被盗。** X2 用一个有效令牌打开站点。他们能列出文件与元数据（T-I3），但没有
   passphrase 或密钥文件就无法解密，没有密钥文件也无法重置 passphrase（T-E3）。*残余风险：*
   在会话过期或被撤销前，元数据暴露。
2. **数据库转储泄露。** X3 取得全部信封。文件是安全的（T-I1）。攻击者针对每个账户的 Argon2id
   信封进行离线字典攻击（T-I2）。*残余风险：*弱 passphrase 会被攻破，强的不会。第 9 节把两者都量化了：
   泄露密码库中的 passphrase 在一台笔记本上不到两天即可攻破，而 4 个随机单词面对一百万台笔记本也能
   撑约两年。
3. **恢复密钥被调包。** X4 登记了自己的恢复公钥。此后每次上传都会把 DEK 包装给 X4（T-S4）。
   上传页面显示的指纹会变，但只有带外比对的用户才会察觉。*残余风险：*影响大，能否发现取决于用户。
4. **未来功能中的 XSS。** 一次脚本注入绕过了 Vue 的转义。它读取两个令牌（T-I4），如果密钥已解锁，
   就能解密它想要的任何内容。它无法导出私钥。*残余风险：*取决于 CSP 能否守住。
5. **未经评审的推送。** 某协作者的电脑被攻破并推送到 `main`（T-E5）。自动部署把它发布出去；这些代码
   可以截获 passphrase（N1）。*残余风险：*整个模型都建立在 `main` 可信的前提上。
6. **已被撤销的接收方。** X7 在撤销之前下载了文件，他们会一直保有它（T-I9、N5）。撤销按设计生效，
   也只能做到这一步。

## 9. Argon2id 成本与 passphrase 最短长度

对应 Issue #60 验收标准第 2 条。要回答的问题是：当前登记的 KDF 成本加上 10 个字符的 passphrase
最短长度，能否让威胁 T-I2（数据库被盗后的离线猜测）处于可接受水平，以及用户在解锁时要为此付出什么。

### 9.1 方法

- **防御方。** `/benchmark/argon2` 运行生产环境的 `deriveKek`——与解锁对话框使用的同一个函数、同一个
  hash-wasm 4.12.0 构建和同一组参数——先不计时运行一次以预热 WebAssembly，再对每组参数各计时运行
  五次，每次使用新的随机盐。测试在本地生产构建（`vite preview`）上运行，执行的是与预发布环境相同的
  代码包。
- **攻击方。** `backend/scripts/benchmark_argon2_offline.py` 使用原生 C 参考实现 argon2-cffi，以相同
  参数先在单核、再在全部核心上运行。
- **同一个函数。** [`test_vectors.json`](crypto/test_vectors.json) 中的 `argon2id_kek` 向量由
  argon2-cffi 生成，浏览器的 `deriveKek` 逐字节复现了它们，因此攻击方的数据适用于真实信封，而不是某个
  相似物。
- **原始数据**保存在 [`benchmarks/argon2id-2026-09-30.json`](benchmarks/argon2id-2026-09-30.json)。

### 9.2 解锁让用户付出的代价

五次运行的中位数，2026-09-30。

| 成本 | Chrome 153，macOS | Safari 18.6，macOS | iOS 26.6（夸克，WebKit） |
|---|---|---|---|
| **64 MiB，t=3（生产环境）** | **100 ms** | **106 ms** | **151 ms** |
| 64 MiB，t=6 | 195 ms | 205 ms | 269 ms |
| 128 MiB，t=3 | 206 ms | 1 327 ms ⚠ | 268 ms |
| 256 MiB，t=3 | 426 ms | 433 ms | 555 ms |

生产环境成本在每个被测客户端上都是 **0.10–0.15 秒**。每次加载页面解锁一次——打开的密钥只存在于页面
内存中——此后每次空闲 15 分钟自动上锁后再解锁一次。当前设置给用户带来的代价可以忽略不计。

关于数据的说明，如实写出而不加修饰：

- **覆盖面很窄。** 只有一台 Apple Silicon Mac 上的两个桌面浏览器引擎，外加一部 iPhone。**没有测量任何
  Android 设备、Firefox，也没有测量低端或较旧的硬件**，而 Argon2id 恰恰在这些设备上最慢。项目从未声明
  支持哪些客户端，因此本文把「支持的客户端」定义为已测集合，并把这一缺口带入发现登记表。
- **Safari 在 128 MiB 时表现异常。** 五次运行都耗时 1.3 秒，比同一浏览器在 256 MiB 时还慢六倍。原因尚
  不清楚。它不影响生产环境成本，但在把参数改为 128 MiB 之前必须先复现它。
- iOS 上的所有浏览器都基于 WebKit，因此夸克的结果可近似代表 iOS Safari。macOS 的 user-agent 字符串显示
  「Intel」是因为浏览器冻结了该字符串；这台机器实际是 Apple Silicon。

### 9.3 参数与公开指南的对照

- **RFC 9106 第 4 节第二推荐选项：** Argon2id，t=3，p=4，m=64 MiB，128 位盐，256 位输出。SecureView 与之
  一致——16 字节盐、32 字节输出——唯一不同是 p=1。hash-wasm 在单线程中依次计算各条通道，因此四条通道
  在相同内存和轮数下耗费的时间与一条相同，对防御方没有任何好处。对这一实现而言，p=1 是如实的设置。
- **OWASP 密码存储速查表的最低要求：** m=19 MiB，t=2，p=1。已超出。
- **服务器的取值范围**（`KeyProtectionProfileIn`）接受 64 MiB–1 GiB 内存、1–10 轮和 1–16 条通道，因此
  提高成本不需要修改后端。

### 9.4 攻击者猜测的代价

一台 10 核 Apple Silicon 笔记本用全部核心每秒可猜 **52.8–58.3 次**，单核每秒 11 次。十个核心只带来 5.3
倍加速，因为每次猜测要占用 64 MiB，瓶颈在内存带宽而非核心数。下表按**每秒 60 次**计算，这是往对攻击者
有利的方向取整。

表中的倍数是假设，不是测量值。本文不对 GPU 或 ASIC 破解 Argon2id 的速度作任何声称；倍数更大时，
每一行都会按比例缩短。

每个账户有自己的盐，因此每个数字都是**针对单个账户**的。

| Passphrase | 1 台笔记本 | 1 000 倍 | 1 000 000 倍 |
|---|---|---|---|
| 位于任何猜测清单的前 10 000 条（`aaaaaaaaaa`、`password12`、`qwertyuiop`） | 2.8 分钟 | 0.2 秒 | 瞬间 |
| 位于一份 1000 万条泄露密码库中的任意位置 | 1.9 天 | 2.8 分钟 | 0.2 秒 |
| 10 个随机小写字母（26¹⁰） | 74 600 年 | 75 年 | 27 天 |
| 4 个随机 Diceware 单词（7776⁴，约 51.7 位） | 190 万年 | 1 930 年 | 1.9 年 |
| 10 个随机可打印 ASCII 字符（94¹⁰） | 2.8 × 10¹⁰ 年 | 2.8 × 10⁷ 年 | 28 400 年 |

表中时间为穷举整个空间所需；成功的期望时间是它的一半。

### 9.5 结论

1. **KDF 成本不是薄弱环节。** 在当前设置下，任何具有约 50 位真实熵的 passphrase——4 个随机单词——都能
   抵御一百万台笔记本数年，而其所有者解锁只需十分之一秒。
2. **10 个字符的最短长度是可用性下限，而不是强度保证。** 检查只看长度，外加「不同于登录密码」。
   `aaaaaaaaaa` 和 `password12` 都能通过，却会在一台笔记本上几分钟内被攻破。当密码由人来选时，长度不能
   很好地代表熵。
3. **只有浏览器能做得更好。** 按设计（O1），passphrase 从不到达服务器，因此服务器既无法对照弱口令名单
   检查它，也无法对它施加任何约束。任何强度检查都必须在客户端进行。

由此向发现登记表（第 4 步）提出两条建议：

- **R-1（关键的一条）：在浏览器中拒绝已知的弱 passphrase。** 套用登录密码的弱口令名单，拒绝重复与连续
  的模式以及账户自身的标识符，并引导用户使用 4 个或更多随机单词。这对缩小上表第 1–2 行与第 4–5 行之间
  差距的作用，远大于任何成本提升。
- **R-2（可选）：提高登记时的成本。** 实测显示存在余量：256 MiB、t=3 在每个被测客户端上最多 0.56 秒，
  并使攻击者每次猜测的成本变为四倍。成本按保护配置分别存储，因此新登记会采用新值，已有账户会在下次
  修改或重置 passphrase 时升级。**在测量过一台低端 Android 设备、并复现 Safari 128 MiB 异常之前，不要
  修改它。**
