## 1. 端到端加密：服务器从头到尾碰不到明文

**讲什么：** 文件在用户浏览器里加密，每个文件都用一把新生成的随机密钥。文件密钥再用 RSA-OAEP 分别包装给用户本人的公钥和
恢复密钥。服务器只收到密文、被包装过的密钥和元数据，没有能力解密。

**证据：**
- `docs/ENCRYPTION_EVIDENCE.md`、`docs/crypto/FILE_ENVELOPE.md`（格式和测试向量）
- CI 里的 `tamper-drill`：篡改服务器上存储的密文，验证客户端一定能发现
- My Files 页面的密文预览面板
- 上传页面的加密过程展示（见第 2 条）

**评委可能问：** 服务器到底能看到什么？
**答：** 文件名、大小、MIME 类型和时间戳这类元数据能看到，这样文件列表和分享才能工作；文件内容和文件密钥看不到。
这一点实话实说，比说"服务器什么都看不到"更可信。

## 2. 「上传一下子就好了，是不是根本没加密？」——上传加密过程展示（PR 进行中）

**背景：** 浏览器里的 AES-GCM 有硬件加速，加密几 MB 的文件只要几十毫秒，所以以前点完按钮瞬间就完成了，看起来像没加密。

**做法：** 上传时分步显示真实流程：读取文件 → 用所选算法加密（新密钥、新 nonce，加密后立刻解密一次自检）→ 用 RSA-OAEP
包装文件密钥 → 只上传密文（真实上传进度条）。每一步旁边标**实测耗时**。最后把原文件的前 16 个字节和加密后的前 16 个字节
**并排显示**：PDF 原文能看到 `%PDF-1.7`，加密后是一串随机字节，那一行就是服务器收到的内容。

**怎么讲：** "我们不靠假装很慢来让人相信加密了。每一步的时间都是实测的，加密前后的字节对比就是证据。"每一步最少停留
0.35 秒，只是为了让人看得清，显示的耗时不含这段停留。

**评委可能问：** 动画是不是做出来的效果？
**答：** 显示的字节是这次上传真实的明文和密文开头，耗时是代码在每一步前后实测的。翻牌效果只是显示方式，最后定格的值是真的。

## 3. 用数据说话的容量测试（#140，PR #155，已合并）

**讲什么：** 导师在 2026-10-01 的会上要求"给数字，不要说支持很多人"。我们写了一个和浏览器做完全相同加密的压测工具，
2026-10-03 至 04 夜间在 staging 上跑完了完整测试矩阵。

**关键数字：**
- 共 22,264 次操作；5,094 次下载全部解密，并和原文件做 SHA-256 比对，**完整性失败 0 次**
- pdf/png/jpg/mp4/zip/exe 六种类型，1 MB 到 500 MB 全部逐字节一致地往返（144/144）
- 5 个用户的混合负载累计稳定运行 108 分钟（19,372 次操作），服务器端零错误；50 个并发用户以内服务器零错误
- 100 个并发用户时开始出错（上传 65–78% 返回 500）。原因是数据库连接池（15 个）耗尽，这时 CPU 平均只有 3%，
  **瓶颈不在硬件**
- 负载降回去以后，服务自己恢复到零错误，不用重启
- 同时登录：服务器按设计同一时间只验证 2 个密码（Argon2id 很耗内存），多出来的请求立刻返回 429 让客户端重试，不会崩

**证据：** `docs/performance/REPORT-2026-10-03.md`（含图表）、`docs/PERFORMANCE_TESTING.md` 末尾的结论、
原始数据 `docs/performance/raw/`、服务器资源采样 CSV。

**一定要说明的测试条件：** 压测端是家里的电脑，所有传输速度都受限于家到服务器这条线路（上行约 24 Mbit/s、下行约
13 Mbit/s），服务器网口本身约 100 Mbit/s。报告里有"Test conditions"一节写明了这些。

**评委可能问：** 为什么 500 MB 要传好几分钟？
**答：** 那是测试线路的带宽，不是服务器的处理速度。服务器 CPU 全程很低，服务器网口上限约 100 Mbit/s，500 MB 至少要
40 多秒。

**评委可能问：** 100 个用户就扛不住了？
**答：** 我们找到了确切的瓶颈：单个 API 进程的数据库连接池，而不是硬件。扩展方法很明确：先确认文件传输期间是否一直占着
数据库连接，再加大连接池、增加 worker 进程，并用同一个工具重新测量。能讲清楚"在哪里坏、为什么坏、怎么扩"，本身就是
这次测试的价值。

## 4. 测试真的找到了 bug，并且修好了（#139 → PR #154）

**讲什么：** 压测工具在本地预演时，就发现了两个只有在并发下才会出现的 MySQL 死锁：两个新账号同时登录，以及下载和分享
同时发生。用户看到的是 HTTP 500。

**修复：** 按 MySQL 官方建议，遇到死锁（1213）或锁等待超时（1205）时回滚并重试整个事务，最多 3 次。

**证据：**
- 新增的回归测试：修复前约 7/10 次能复现死锁，修复后每次都通过
- 后端完整测试 627 个全部通过，覆盖率 85.17%
- staging 整晚 28,540 个请求，没有出现一次死锁

**怎么讲：** "我们的测试不是走过场。它在上线前发现了真实的并发 bug，我们修好了，并用测试证明修好了。"

## 5. 监控和告警是真的会响的

**讲什么：** `mcs21-observe` 每 5 分钟检查一次错误数、登录限流、磁盘、审计链检查点等指标，超过阈值就发邮件。
压测那晚，三次故意制造的过载各自触发了一封告警邮件（22:25、00:45、02:45），并在下一次检查时自动解除。

**证据：** 告警邮件截图（你的邮箱）、`docs/OBSERVABILITY_AND_INCIDENT_RESPONSE.md`、压测报告摘要里的 Monitoring 一行。

## 6. 运维上的专业做法（可以作为项目管理和部署的亮点）

压测前通知团队；暂停备份、异地备份、对账、完整性巡检、安全 Agent 和自动部署，避免它们干扰测试，也避免备份把测试数据
一起备份进去；只为压测临时给 SSH 开一个最小的端口例外，测完撤销；测完通过 API 删除全部测试账号和文件，磁盘恢复到基线；
手动补跑当晚的备份，再恢复所有定时任务；全过程记录在 PR #155 里。

## 7. 防止恶意大量上传 / 拖垮服务器

**现有防护：**
- 只有通过邮箱验证码注册的账号才能上传；注册和发验证码都有频率限制
- nginx 按 IP 限速：API 每秒 10 次（突发 20），登录每分钟 12 次
- 单个文件最大 500 MB；nginx 会先收完整个上传再交给后端，网速很慢的客户端占不住后端
- 磁盘超过 85%、错误突增都会发告警邮件；安全 Agent 能识别暴力猜密码、下载突增、分享突增

**已知缺口：** 威胁模型里本来就记录了（`docs/THREAT_MODEL.md` T-D2 / F-09）：没有单用户存储配额。一个账号理论上
就能把磁盘填满，目前只有 85% 告警，没有拦截。

**「计划中」的加固**（做完后把这一节改成"已完成"并补上 PR 号）：
1. 单用户配额（暂定每人 2 GB、每天 5 GB），超出时给出明确提示；磁盘剩余空间低于底线时拒绝所有上传
2. nginx 限制每个 IP 同时最多 3 个上传连接
3. 安全 Agent 新增 `UPLOAD_BURST` 规则
4. 下载可执行文件或带宏文件（.exe、.bat、.js、.docm 等）时弹出警告

**大流量 DDoS 要如实说：** 这种攻击在应用层防不住，100 Mbit/s 的网口很容易被打满。真正上线时应该在前面放 Cloudflare
这类防护服务。把它写成"超出本项目范围的已知风险"，比假装能防住更专业。

**怎么讲：** "我们先做了威胁建模，知道哪里有缺口，按风险排了优先级，再一项项补上。"

## 8. 为什么不扫描病毒——零知识加密的取舍

**讲什么：** 服务器只能拿到密文，就算装了杀毒软件，扫到的也是随机字节，所以无法在服务端扫毒。这是端到端加密的必然
结果，不是疏漏；其他端到端加密网盘（如 Proton Drive）同样不能在服务端扫描文件内容。

**我们怎么弥补：**
- 文件只能分享给上传者明确指定的注册用户，没有公开链接，风险相当于"认识的人发来的邮件附件"
- 文件在浏览器解密、保存到电脑后，系统自带的杀毒软件（Windows Defender、macOS XProtect）会照常扫描
- 「计划中」：下载可执行文件或带宏文件时给出警告
- 我们**有意不**把文件哈希发给 VirusTotal 这类服务，否则会把"谁有哪个文件"泄露给第三方

**怎么讲：** "隐私和服务端扫毒不能兼得。我们选了隐私，并用分享范围、下载警告和终端杀毒来降低风险。"
