# 后端架构

[English](ARCHITECTURE.md) | [简体中文](ARCHITECTURE.zh-CN.md)

## 架构决策

后端采用**模块化单体（modular monolith）**架构。这符合 FYP 的范围：一个可部署的
FastAPI 应用和一个 MySQL 数据库，并在内部维持严格的边界。微服务会引入分布式事务
和额外的运维工作，却无法改善当前安全模型。

本架构有意保持务实。只有当抽象能够保护真实边界（数据库、存储、密码学、身份）时
才引入它，而不是仅仅为了增加目录层级。

认证（Auth）是第一个已完成、由数据库支持的纵向功能切片。文件、共享、审计查询、
恢复及管理员路由的用例仍是脚手架，因此这些路由继续以 `501 feature_not_implemented`
失败关闭（fail closed）。

## 依赖方向

```text
HTTP router / dependency
          |
          v
Application service (one use-case transaction)
          |
          +----> repository / unit-of-work
          +----> storage port
          +----> crypto capability
          +----> domain policy
```

规则：

1. 路由负责校验 HTTP 输入、取得已认证行为者、调用一个应用服务，并将结果映射到响应
   Schema。路由不得包含 SQL、文件系统或密码学逻辑。
2. 应用服务负责协调用例。依赖项必须通过构造函数注入，应用服务绝不能在内部创建
   数据库 Session 或基础设施适配器。
3. 一个命令型用例只拥有一个数据库事务。Repository 可以执行 `flush`，但绝不能自行
   `commit`。
   滥用控制计数器是有意设置的前置条件例外：它们单独提交，防止被拒绝或回滚的注册、
   登录操作抹去自身的限流证据。受保护的领域变更仍只拥有一个原子事务。
4. 能力服务（密码学、哈希、水印、存储）不得导入应用服务，从而让依赖图保持无环。
5. ORM Model 是持久化模型，绝不能跨越 API 边界。Pydantic Schema 是传输模型，绝不能
   包含 SQLAlchemy 行为。
6. 配置和应用组合只能发生在进程边界（`core/config.py` 和 `main.py`）。任何模块都不得
   依赖当前工作目录。

## 包职责

```text
backend/app/
|-- api/                 FastAPI 路由、依赖项、错误/响应映射
|   `-- v1/              版本化公开 API 及其组合路由
|-- core/                配置、数据库/Session 工厂、安全基础组件
|-- domain/              可信上下文、不可变结果、枚举、公开领域错误
|-- models/              SQLAlchemy 持久化模型
|-- repositories/        永不自行提交事务的持久化操作
|-- schemas/             Pydantic 请求/响应 DTO
|-- services/            应用用例及小型能力服务
|-- utils/               仅限纯函数、无依赖的辅助工具
`-- main.py              应用工厂与组合根

backend/migrations/      Alembic Schema 历史（Schema 的唯一事实来源）
backend/tests/
|-- unit/                纯策略、密码学、校验及服务测试
|-- api/                 FastAPI 契约及依赖覆盖测试
`-- integration/         MySQL、迁移、Repository 及存储测试
```

认证纵向切片引入了具体的 `AuthRepository`；SQLAlchemy 的请求级 `Session` 是其工作单元，
`AuthService` 是事务所有者。存储端口会随第一个由存储支持的纵向切片一同引入。本项目
有意避免空泛的通用基类。

## 身份与授权边界

Session 模型使用两个相互独立的高熵不透明凭据，而非 JWT：

- 短期 access token 是 Bearer 凭据。服务器端 Session 行只存储它的 SHA-256 哈希。
  一个统一的 API 依赖项将其解析为可信的 `ActorContext`，其中包含内部及公开的用户/
  Session ID、角色、状态，以及已经校验的 access-token 哈希。
- refresh token 作为独立的、带 generation 编号的哈希记录存储。它只能使用一次：刷新
  成功后会被消费，并同时轮换两个凭据。重复使用已经消费的 refresh token 会被视为
  重放攻击，撤销整个 Session family，并追加一条审计事件。绝对 Session 过期时间阻止
  无限期刷新。
- 刷新轮换在持有 Session 锁期间强制执行可配置的最小间隔，从而限制单个账户增加 token
  generation 及全局审计事件的速度。
- 登出会撤销当前 access/refresh family。全部登出及修改密码会撤销该账户所有活跃的
  family。活跃 Session 数量限制会淘汰最早的 Session。

密码先以 Unicode NFC 规范化，长度必须为 15 至 128 个字符，不得等于规范化后的用户名、
电子邮箱或邮箱本地部分，并使用 `pwdlib` 推荐的 Argon2id 哈希器。登录使用
`verify_and_update`，因此参数变化时可升级已存储的哈希；验证器接受旧版 bcrypt 记录，
并在验证成功后将其替换为 Argon2id。未知或格式错误的哈希会按无效凭据处理；对于未知
用户，系统仍会执行一次有效的虚拟哈希验证，以降低基于时序的账户枚举风险。仓库自带的
常见密码阻止列表有意保持小型且仅存于本地。它是本 FYP 的安全基线，不能替代生产环境中
持续维护的泄露密码语料库。

内存密集型密码操作使用由同一 worker 共享、并根据该 worker 内存预算配置的有界信号量。
获取信号量时绝不会在共享同步线程池中等待：worker 容量耗尽时返回带 `Retry-After` 的
`429`，且不会将其记录为一次密码失败。该容量限制独立于账户/IP 失败阈值；多 worker
部署必须将每进程预算相乘评估，并仍需在边缘层执行并发限制。

登录限流信息持久化在 MySQL 中，分别使用规范化账户和客户端 IP bucket；注册使用一个
IP bucket。Bucket 标识符是以应用密钥为 key 的 HMAC-SHA-256 值，因此用户名和 IP 地址
不会以明文限流 key 存储。账户和 IP 阈值分开配置，避免把较小的单账户限制套用到整个
共享网络。登录和密码重新认证在 Argon2 运行前，会按排序顺序对独立的失败 bucket 加行锁
并检查；验证完成后的失败会被记录，同时独立的 worker 容量门限制进行中的工作量。注册
会在取得同一把锁后重新检查阻止状态。这样可以让限流在各应用 worker 之间保持一致，
但代理 IP 信任、保留/清理策略，以及分布式边缘层滥用防护仍属于部署层面的责任。

注册会在一个事务中创建用户、RSA 公钥/指纹及审计事件。匹配的私钥绝不会被持久化，
只会在不可缓存的 TLS 响应中返回一次。因此，如果注册响应丢失，就必须依赖未来的密钥
恢复/轮换流程；服务器无法重新生成该私钥。

忘记密码重置、电子邮箱验证、MFA 及外部身份联合尚未实现。它们需要可信的带外传递、
注册或身份提供商通道，而不是增加更多未认证的数据库端点。`email_verified` 当前是预留
元数据，并非登录条件。

每个非公开端点都必须要求该上下文。角色检查发生在 API 边缘；资源检查在用例内部使用
行为者 ID 完成。文件访问始终同时要求：

1. 存在具备所需能力且仍然有效的逻辑访问授权；以及
2. 同一用户和同一文件存在仍然有效的已包装文件密钥。

默认授权结果为拒绝。管理员、审计验证和恢复路由必须声明明确角色。恢复流程采用经办-
复核分离（maker-checker separation）：请求者不能批准自己的请求。

## 事务与存储边界

MySQL 事务无法与本地文件进行原子提交。因此，上传采用暂存写入与补偿机制：

1. 校验大小/类型，并以流式方式加密明文，将其写入随机暂存对象；
2. 计算加密后哈希，并在内存中包装文件密钥；
3. 为文件元数据、所有者授权、密钥包装及审计日志开启一个数据库事务；
4. 以原子方式将暂存对象重命名为最终不透明对象 key；
5. 提交数据库事务；
6. 任何步骤失败时回滚，并移除暂存/最终对象；定期孤儿扫描负责处理重命名后、提交前
   进程崩溃的情况。

数据库行只存储不透明的存储对象 key，绝不存储主机文件系统路径。下载和加密工作不得
阻塞异步事件循环；有界的阻塞工作在线程池中运行。必须在读取无界请求体之前拒绝超出
大小限制的请求。

## 密码学边界

- 每个文件拥有独立的 256-bit AES key 和 96-bit GCM nonce。
- 加密对象采用带版本的 envelope。稳定的文件身份、密码学版本，以及所有者/文件 ID
  作为 AES-GCM associated data 接受认证。
- AES key 只在内存中存在足以完成包装/解包的时间，绝不能进入 API DTO、应用日志、
  异常或数据库明文列。
- RSA-OAEP 使用 SHA-256；加载后的 key 必须校验类型、最小长度及指纹。
- 本 FYP 的服务器端解密流程可能会短暂接收用户私钥。此类端点必须禁用请求体日志，
  且绝不能持久化私钥。这是明确的原型限制，不是生产级密钥托管设计。
- 恢复私钥操作与普通用户端点隔离，并接受完整审计。

## 审计完整性

审计写入与安全敏感操作属于同一个事务。认证模块目前通过使用
`SELECT ... FOR UPDATE` 锁定的单例 `audit_chain_heads` 行进行追加；该行记录最后一条日志
和当前哈希，因此并发事务无法让链产生分叉。迁移只会在审计表为空时写入 genesis。由于
revision `0001` 使用不同的规范化 payload 且丢失了 datetime 的微秒，`0002` 会拒绝升级
非空的旧版审计表；接管此类表需要经过评审的迁移和外部 checkpoint。新时间戳保留六位
小数，缺失的 metadata 以 `{}` 规范化存储，因此可依据持久化值重新计算各行。用户引用
采用限制型外键，因为级联更新 ID 或硬删除会改变已被哈希的历史；因此账户删除必须继续
采用基于状态的软删除。只驻留于数据库的普通哈希链可以检测意外修改，却无法阻止数据库
管理员重写并重新计算历史；若要获得更强的防篡改证据，仍须定期在审计数据库之外保存
签名/HMAC checkpoint。

## Schema 与交付规则

- ORM metadata 加 Alembic migration 是唯一的 Schema 权威。
- 应用绝不调用 `create_all()`，也绝不在启动时运行破坏性 SQL。
- 空数据库必须能够通过 `alembic upgrade head` 达到当前 Schema。
- MySQL 专用集成测试使用 MySQL 8.4，而非 SQLite 替代品。
- 合并前必须通过格式检查、lint、单元/API 测试、migration upgrade 和 migration drift
  检查。

## 用例就绪定义

只有满足以下条件后，功能才可开始实现：

- 请求与响应 Schema 不包含秘密/内部字段；
- 已明确认证、角色及资源策略要求；
- 已指定一个事务所有者及其回滚行为；
- 在适用场景中已定义存储清理/补偿行为；
- 已定义稳定的领域错误码和审计事件；
- 已包含单元测试，以及覆盖正常路径和一条拒绝路径的 API 或集成测试。
