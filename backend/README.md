# Backend

FastAPI modular-monolith backend for the secure file encryption and sharing platform.

## Current Status

The Auth vertical slice is implemented and no longer guarded by the draft-route dependency.
It owns real MySQL transactions, opaque access and rotating refresh credentials, session
revocation, login/registration throttling, user RSA registration keys, and chained audit
events. These nine endpoints are active under `/api/v1`:

| Method | Endpoint | Authentication |
|---|---|---|
| POST | `/auth/register` | Public |
| POST | `/auth/login` | Public |
| POST | `/auth/refresh` | Refresh credential |
| GET | `/auth/me` | Bearer access token |
| POST | `/auth/logout` | Bearer access token |
| POST | `/auth/logout-all` | Bearer access token |
| POST | `/auth/change-password` | Bearer access token |
| GET | `/auth/sessions` | Bearer access token |
| DELETE | `/auth/sessions/{session_id}` | Bearer access token |

File, sharing, audit-query, recovery, and admin endpoints remain contract scaffolds and
deliberately return `501 feature_not_implemented`. `/health/live` and OpenAPI remain
available. Unguard those routers only after their authorization, persistence, transaction,
audit, storage, and denial tests are complete.

The password policy normalizes with Unicode NFC, requires 15 to 128 characters, rejects
account-derived/common values, and hashes with Argon2id. Valid legacy bcrypt hashes are
transparently upgraded; memory-hard operations fail fast when the configured per-worker
capacity is full. The included common-password list is a small local safety baseline, not a
maintained breached-password corpus. Forgotten-
password reset, email verification, MFA, and external identity login are not implemented;
each needs a trusted out-of-band delivery or identity channel.

## Prerequisites

- Python 3.11 or newer
- Docker with Compose (recommended for MySQL 8.4)

The canonical command directory for backend commands is `backend/`. Configuration always
loads the repository-root `.env`, and configured relative storage paths are resolved from
the repository root rather than the process working directory.

## First Setup

From the repository root, create `.env` only if it does not already exist:

Before running `alembic upgrade head`, confirm the target database is clean or already has
an `alembic_version` row. The currently inspected local legacy database does not; follow
the [database adoption policy](../docs/DATABASE_SCHEMA.md#adopting-a-legacy-development-database)
instead of running or stamping the normal history against it.

```powershell
Copy-Item .env.example .env
docker compose up -d mysql
Set-Location backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
alembic upgrade head
```

macOS/Linux activation command:

```bash
source .venv/bin/activate
```

Do not commit `.env`, private keys, recovery keys, runtime files, or encrypted test data.

## Run

Development:

```bash
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

OpenAPI: <http://localhost:8000/docs>

Liveness: <http://localhost:8000/health/live>

`--reload` is for local development only. A deployment must use injected non-default
secrets, `APP_DEBUG=false`, explicit CORS origins, and a supervised process/container.

## Quality Checks

Run from `backend/`:

```bash
ruff format --check app tests migrations scripts
ruff check app tests migrations scripts
pytest
alembic check
pip-audit -r requirements.txt
```

Integration tests that exercise ORM behavior must use MySQL 8.4 because the schema uses
MySQL-specific unsigned integers, enums, binary columns, collation, JSON, and referential
actions. Do not substitute SQLite for those tests.

## Database Changes

Alembic owns schema evolution. The application never calls `create_all()` and Compose no
longer mounts a destructive table-initialisation script.

```bash
alembic upgrade head
alembic revision --autogenerate -m "describe the change"
alembic check
```

Review every autogenerated revision before committing it.

For staging or production, use the guarded deployment runner rather than invoking Alembic
with the runtime database account:

```bash
python -m scripts.deploy_mysql
python -m scripts.verify_mysql
```

An existing managed database that is behind head also requires `--confirm-backup`. Account
provisioning and all required environment variables are documented in
[DEPLOYMENT.md](../docs/DEPLOYMENT.md).

If an older local database was created by the former `docs/init.sql`, read the legacy
adoption warning in `docs/DATABASE_SCHEMA.md` before upgrading; do not run `upgrade head`
against it or stamp it blindly. The Auth migration safely follows the Alembic baseline but
does not turn an unmanaged legacy schema into an Alembic-managed one.

## Architecture Rules

The concise rules and security/transaction boundaries are documented in:

- [Backend architecture](../docs/ARCHITECTURE.md)
- [Database schema policy](../docs/DATABASE_SCHEMA.md)
- [Security flows](../docs/SECURITY_FLOWS.md)
- [API design](../docs/API_DESIGN.md)

The key dependency rule is: router -> use-case service -> repository/storage/crypto policy.
Routers contain no SQL or filesystem logic; repositories never commit; one use case owns
the transaction and storage compensation behavior.
